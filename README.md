# sprut-agent

**Agent-first интеграция для умного дома на SprutHub.**

[![CI: GitHub Actions](https://img.shields.io/badge/CI-GitHub_Actions-24292F?logo=githubactions&logoColor=white)](https://github.com/xor777/sprut-agent/actions/workflows/check.yml)
[![Node.js 24+](https://img.shields.io/badge/Node.js-24%2B-417E38?logo=nodedotjs&logoColor=white)](package.json)
[![MIT License](https://img.shields.io/badge/License-MIT-2563EB)](LICENSE)

sprut-agent создаётся, чтобы поручать ИИ работу с домом: понимать устройства,
настраивать автоматизации и разбираться в их поведении. Интеграция даёт агенту
программный доступ к SprutHub; сам хаб остаётся местом исполнения сценариев.
Подробнее о целевом опыте — в [видении продукта](https://plan.nuanu.ai/project/SPRUT/docs/176).

> [!IMPORTANT]
> Проект на ранней стадии. Чтение проверено на настоящем SprutHub и с агентом.
> На целевом хабе с внешним агентом проверены создание и изменение BLOCK,
> повтор без дубля, восстановление в новом диалоге и сохранение чужой правки.
> Проверены команда лампе и один естественный цикл автоотключения.
> Повторное событие датчика внутри минуты ещё не подтверждено.
> Прямой вход по логину и паролю, сохранение сессии и повторный запуск проверены
> владельцем на настоящем SprutHub 2026-09-10 без передачи секретов агенту.

## Что есть сейчас

| Часть | Возможности | Готовность |
| --- | --- | --- |
| Подключение | Нативный вход по логину и паролю из локального файла; получение домов и сохранение сессии | Вход, чтение дома и повторное использование сессии после перезапуска проверены на настоящем хабе |
| Исследование протокола | Извлечение схем, сравнение снимков, пассивная запись WebSocket-трафика | Доступно в `main`; ограничения extractor описаны ниже |
| MCP-интеграция | Выбор доступного дома, компактный каталог и чтение нативных комнат, устройств, сервисов, характеристик, сценариев, расширений, логик и настроек по устойчивой ссылке | Сквозное чтение проверено на одном живом доме и свежим агентом; разделение двух домов — офлайн |
| Автоматизация | Preview и идемпотентное применение boolean → boolean BLOCK; подготовка, применение, сверка и защищённое восстановление ограниченных нативных изменений | Поддержанные BLOCK/property, история и защищённое восстановление проверены на целевом хабе; это не полный охват сценариев и настроек |
| Наблюдения на хабе | Агент читает температуры и параметры мультисенсора; MCP получает обновления при повторном чтении и восстанавливает связь | Проверено на одном Sprut.hub 2; это не гарантия совместимости со всеми версиями |

Рабочий сценарий MCP — вопрос «Какая температура в офисе?».
Агент сначала получает доступные дома, явно выбирает дом, затем получает исходные
названия комнат, выбирает подходящую и читает её данные.
Смысл запроса разбирает агент; интеграция отвечает за идентификаторы, значения,
единицы и свежесть.

Нативный write-path умеет менять одно типизированное значение характеристики,
создавать BLOCK в опубликованном ограниченном формате и полностью заменять
`data` существующего BLOCK. Каждое изменение сначала сохраняет baseline и diff,
а после отправки отдельно сообщает ACK и readback. Создание произвольного кода,
GLOBAL/LOGIC, pairing, backup и поток данных для дашбордов не реализованы.
Специализированный `MotionDetected=true` → `On=true` preview остаётся доступен и
может добавить автоотключение через заданное число секунд.

## Из чего состоит проект

Один пакет на JavaScript, Node.js и npm. У исследовательских инструментов
самостоятельные команды; MCP-сервер запускается одним процессом.

| Компонент | Зачем нужен |
| --- | --- |
| [MCP-сервер](src/server.mjs) | Предоставляет агенту чтение нативной модели дома и инструменты автоматизации; использует официальный MCP SDK и Zod |
| [Подключение к SprutHub](src/spruthub-connection.mjs) | Выполняет нативный вход, проверяет полученную сессию и сохраняет её локально для следующего процесса |
| [Клиент SprutHub](src/spruthub-client.mjs) | Выполняет узкий набор нативных запросов через WebSocket, преобразует ответы и ошибки хаба |
| [Исследовательские утилиты](research/) | Помогают наблюдать протокол и находить изменения между сборками интерфейса |
| [Журнал протокола](research/protocol/) и [снимки](research/snapshots/) | Сохраняют источники, версии и границы подтверждённого поведения |

Путь запроса:

```text
ИИ-агент → MCP по stdio → sprut-agent → JSON-RPC по WebSocket → SprutHub
```

Основной путь работает через протокол хаба и не зависит от расположения кнопок
в интерфейсе. Изменения самого протокола всё ещё могут потребовать обновления
клиента — поэтому наблюдения и проверка на конкретной версии входят в работу.

## Быстрый старт

Нужны **Node.js 24+**, npm и доступ к репозиторию. Следующие команды проверяют
инструменты из `main` локально; подключение к дому не требуется.

```sh
git clone https://github.com/xor777/sprut-agent.git
cd sprut-agent
npm ci
npm run check
```

Попробовать сравнение на включённом в репозиторий снимке:

```sh
npm run research:diff -- \
  --from research/snapshots/1.5.58 \
  --to research/snapshots/1.5.58
```

Это сравнение снимка с самим собой: ожидается `Verdict: unchanged`.
Для содержательного сравнения передай два разных каталога снимков.

### Skill для Codex

Если MCP `sprut` уже подключён, установи skill из этого репозитория обычной
ссылкой в пользовательский каталог Codex:

```sh
mkdir -p "$HOME/.agents/skills"
ln -s "$PWD/skills/spruthub-master" "$HOME/.agents/skills/spruthub-master"
```

Codex обнаруживает изменения skill автоматически; если он не появился в списке,
перезапусти Codex. Skill не настраивает MCP и не расширяет доступ к дому: он
использует только уже подключённые публичные инструменты `sprut` и полномочия
текущего запроса. Поддержка локальных skill-каталогов и символьных ссылок описана
в [официальной документации Codex](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills).

Один переносимый read-only smoke устанавливает копию skill в новый временный
`HOME`, запускает публичный MCP на синтетическом хабе и сохраняет доказательства
в отдельный временный каталог вне репозитория:

```sh
npm run eval:spruthub-master
```

Команда требует локально аутентифицированный Codex CLI. Она подключает
существующий `auth.json` к временному профилю символьной ссылкой, не копирует
его в репозиторий или результат и не обращается к живому дому. Для ручной
проверки другого принятого кейса и режима передай их после `--`, например
`npm run eval:spruthub-master -- native-option treatment`.

## Найти дом и прочитать нативный объект через MCP

Основной read-only путь начинается с `list_homes`: инструмент возвращает дома,
доступные учётной записи, а при единственном результате указывает его как выбор
по умолчанию. `inspect_home` принимает явный `home_ref` и раскрывает небольшой
каталог комнат, сценариев и расширений. `get_entity` читает выбранную комнату,
устройство, сервис, характеристику, сценарий, расширение, назначенную логику или
окно физических настроек. Опции, связи, физическая конфигурация и объёмная
диагностика раскрываются только через `include`. `include` применяется к
указанной сущности, а не рекурсивно ко всем её детям. Безопасная характеристика
возвращает `option_scope`: нативную доступность options как `true`, `false` или
`null`, состояние фактического чтения и точный следующий вызов. Только реальный
совместимый ответ `characteristic.getOptions` с явным массивом даёт `found` или
`checked_empty`; отсутствующий или неверный operation container возвращает
`incompatible_response`, а не пустой результат. Каждый запрошенный include
перечислен в `include_resolution.applied` или `not_applied`. Для неприменимого
include ответ даёт следующий исполнимый вызов по безопасной возвращённой ссылке,
когда такая ссылка известна, иначе явно сообщает ограничение. Отсутствие массива
не означает, что все дочерние области проверены. Физическое окно и назначенная
логика остаются отдельными владельцами настроек. Terminal redacted marker не
получает `include_resolution` и не раскрывает ссылки.

Все новые ссылки квалифицированы домом: `spruthub://hub/<serial>/room/<id>` и
`spruthub://hub/<serial>/accessory/<aId>/service/<sId>/characteristic/<cId>`;
serial кодируется как компонент URI. Поэтому одинаковые локальные ID двух домов
не смешиваются. Код и диагностический текст сценариев и устройств возвращаются
как недоверенные данные. Распознанная credential/PASSWORD-сущность целиком
заменяется явным redacted marker, включая её значения, потомков и native
identifier. Свободный текст с известным credential-представлением скрывается
целиком; произвольный секрет невозможно распознать математически полно.
Классификация выполняется по исходным native metadata до построения публичного
ответа. В `read_room` marker является отдельным валидным вариантом reading,
поэтому обычные соседние показания остаются доступны. Marker терминален:
`include` не раскрывает его потомков и не запускает дополнительные чтения.
Если точное значение текущего connection token встречается в JSON-key,
скрывается только ближайший содержащий этот ключ объект.

`list_rooms` использует дом по умолчанию. `read_room` принимает квалифицированную
ссылку любого доступного дома; чтение другого дома не меняет выбор по умолчанию
или привязку автоматизаций. Агент сопоставляет слова пользователя с каталогом;
поиск по имени внутри интеграции не выполняется.

Результат чтения сохраняет ссылки комнаты, устройств, сервисов и характеристик,
контекст сервиса, доступность, значения и единицы. Для нативного перечисления
рядом с исходным значением возвращается `enum` с ключом и названием; неизвестный
код остаётся исходным значением с `enum: null`. В `readings` попадают только
характеристики, которые хаб явно пометил доступными для чтения. Пустой `devices` означает существующую пустую комнату.
Неверная, устаревшая или относящаяся к другому дому ссылка даёт
структурированную ошибку с предложением снова вызвать каталог.

Настрой подключение локально. Владелец хранит только логин и пароль в файле вне
репозитория; значения не должны попадать в Git, логи или ответы инструмента:

```sh
mkdir -p "$HOME/.config/sprut-agent"
touch "$HOME/.config/sprut-agent/connection.env"
chmod 700 "$HOME/.config/sprut-agent"
chmod 600 "$HOME/.config/sprut-agent/connection.env"
```

Содержимое `~/.config/sprut-agent/connection.env`:

```dotenv
SPRUTHUB_LOGIN=owner@example.com
SPRUTHUB_PASSWORD=local-secret
```

Штатный `npm start` и прямой запуск сервера сами читают этот файл. После его
создания перезапусти то же MCP-приложение; менять уже настроенные command, args
или env не нужно:

```sh
npm start
```

По умолчанию используется beta endpoint `wss://beta.spruthub.ru/spruthub`.
Для другого сервера добавь `SPRUTHUB_URL` в тот же файл. После нативных шагов
`account.auth` и `account.answer` полученная сессия проверяется через `hub.list`
и атомарно сохраняется в `~/.config/sprut-agent/session.json` с режимом `0600`.
Следующий процесс сначала проверяет эту сессию и входит заново только при
подтверждённом отказе авторизации. Путь можно изменить через
`SPRUT_AGENT_SESSION_FILE`.

Прямой вход из локального файла, чтение температур и повторное чтение новым
MCP-процессом с сохранённой сессией проверены на настоящем SprutHub 2026-09-10.
Разделение чтения и записи между несколькими домами проверено офлайн;
это не живая проверка нескольких хабов.

Если переменных нет, любой публичный инструмент возвращает ошибку
`configure_credentials`. Основное сообщение и `credential_setup` содержат
абсолютный путь текущего профиля, обязательные поля, права `0600` и просьбу
перезапустить то же MCP-приложение. Логин и пароль всё равно создаются владельцем
локально: их нельзя передавать агенту в чате. Полный явно переданный профиль —
логин с паролем либо token с URL и CID — не читает default `connection.env`,
поэтому значения другого профиля и состояние этого файла на него не влияют. При
неполном профиле явно переданные процессу `SPRUTHUB_*` значения имеют приоритет
над файлом; из файла читаются только поддержанные параметры подключения,
остальные ключи не применяются к процессу. Явное пустое значение файл не
заменяет. Нечитаемый, не обычный или доступный другим пользователям файл, когда
он нужен, даёт исправимую ошибку `credential_file_unavailable`, а не
притворяется отсутствующим.

Если учётной записи доступен один дом, он безопасно выбирается для операций без
квалифицированной ссылки. При нескольких домах `list_homes`, `inspect_home`,
`get_entity` и `read_room` позволяют явное чтение по home-qualified ref, но это
не становится неявным выбором для будущей записи. Для `list_rooms` и всех
операций автоматизации добавь явный `SPRUTHUB_SERIAL`; без него сервер вернёт
`home_selection_required` до записи.

Ранее настроенный путь с готовой сессией остаётся доступен: укажи
`SPRUTHUB_URL`, `SPRUTHUB_TOKEN`, `SPRUTHUB_SERIAL` и `SPRUTHUB_CID` вместо
логина и пароля. `SPRUTHUB_TIMEOUT_MS` необязателен; по умолчанию весь вход или
один обычный запрос ждёт не более 10 секунд. CAPTCHA, подтверждение по коду,
регистрация нового пароля, выбор хаба внутри auth-flow и перенаправление не
угадываются: сервер останавливается с исправимой структурированной ошибкой.

`freshness.hubResponseReceivedAt` — локальное время получения полного ответа
хаба. `measurementAt: null` означает, что подтверждённое время самого измерения
не получено; время ответа не выдаётся за время измерения. Каждый вызов читает
данные заново. После временной ошибки можно повторить тот же инструмент в том же
MCP-сеансе; успешный старый ответ не кэшируется. В нативной модели
`source_timestamp: null` означает, что SprutHub не вернул время источника.
Настроенное значение, диагностика устройства и `pending: "unknown"` остаются
разными фактами и не выводятся друг из друга. В этом срезе адаптер не связывает
HTML-диагностику с option: ни суффикс native key, ни совпадение имени свойства не
дают полной общей identity, поэтому structured `reported_value` остаётся `null`.
Безопасная диагностика доступна отдельно через `include=diagnostics`.

Ссылка расширения строится только из непустого native `extensionKey`. Отсутствие
или конфликт этого ID даёт `incompatible_response`, а не alias из общего `type`.

`inspect_home.coverage` перечисляет только операции, завершившиеся в этом
вызове; успешный `list` не подтверждает `get` или `window.get`. Неподдержанный
метод (`-32601`), отказ доступа и отсутствие ответа различаются как
`unsupported`, `insufficient_access` и `unknown`. Строковый native `owner`
сохраняется отдельно, а право ownership без boolean-доказательства остаётся
`unknown`.

Read-only envelope `room.list`, `room.get` и фильтрованный по `roomId`
`accessory.list` наблюдались 2026-09-09 на Sprut.hub 2 с прошивкой
`3.0.0b (20131)`; обезличенный источник и границы — в
[`research/protocol/2026-09-09.md`](research/protocol/2026-09-09.md).
В новом диалоге Codex проверен путь «офис» → каталог → выбранная комната →
обе температуры настоящего хаба. В отдельной живой проверке разрыв соединения
интеграции дал исправимую ошибку, а следующий вызов в том же MCP-процессе
восстановил чтение. Инструменты чтения ничего не записывают в дом.

Расширенный путь `list_homes` → `inspect_home` → `get_entity` проверен на том же
хабе: комнаты, физические настройки датчика, назначенные логики, разные экземпляры
расширений и конфигурации BLOCK/GLOBAL. Свежий Codex gpt-5.6-terra/medium прочитал
настоящий BLOCK и объяснил отсчёт таймера от события хаба, сохранив неопределённость
относительно последнего физического движения. Это один проверенный запрос,
а не оценка готовности агента ко всем задачам дома. Доказательства и ограничения —
в [приёмке модели дома](https://plan.nuanu.ai/project/SPRUT/issue/18).

На настоящем мультисенсоре физическое изменение освещённости дважды дало новое
значение с прежней ссылкой характеристики; источник и границы — в
[наблюдении от 2026-09-09](research/protocol/2026-09-09-motion.md). Позднее
переход движения `false → true` запустил созданный BLOCK и физически включил
целевое устройство; свидетельство — в
[исследовании автоматизаций](research/protocol/2026-09-09-automations.md).
В отдельных синтетических диалогах агент
сохранил исходные имена двух подходящих офисов при одинаковых и разных
показаниях, но эти примеры не гарантируют поведение любой модели и формулировки.
На этом же мультисенсоре сопоставлены все 16 читаемых характеристик; новый
диалог агента правильно объяснил нативные состояния разряда и зарядки.
Проверенный агентный клиент — Codex CLI 0.153.4, gpt-5.6-sol/xhigh.
Доказательства и границы принятого среза — в
[задаче живой приёмки](https://plan.nuanu.ai/project/SPRUT/issue/4).

## Preview, применение и откат автоматизации

Для общего нативного изменения сначала вызови `get_native_change_contract`,
затем `prepare_native_change` и проверь сохранённые baseline и diff. Поддержаны
операции `characteristic_value`, `block_create` и `block_data_update`; последняя
заменяет только полное `data`, не имя и runtime-флаги сценария.
`apply_native_change` сохраняет намерение перед отправкой, отдельно возвращает
его направление apply/restore, нативный ACK и результат повторного чтения.
Перед новой отправкой инструмент заново проверяет native contract, bindings и
конкретные значения. При `uncertain` не повторяй запись: вызови
`get_native_change`. Его `verification.fresh=false` явно означает, что новый
readback не получен; сохранённый исход операции от этого не становится свежим
доказательством. `restore_native_change` восстанавливает BLOCK только пока
текущая конфигурация совпадает с применённым снимком; завершённый `restored`
терминален для этого change ref, а значение физической характеристики инструмент
не откатывает. `list_native_changes` находит по дому и необязательной canonical
entity ref сценарий и участвующие accessory/service/characteristic до и после
изменения, включая старые записи automation API. Его `recorded_status` —
сохранённый исход на `updated_at`, а не текущая проверка хаба; для неё вызови
возвращённый `next`. Обнаружение записи в истории не является разрешением на её
восстановление.

BLOCK-контракт версии `2026-09-10` допускает корневой `targets`, вложенные `if`
в режиме `EVERY`, условия `AND`/`OR` и типизированные characteristic comparisons,
действия service/set и delay `RESET`. Нативные `aId/sId/cId` и типы проверяются
по выбранному дому. При сравнении снимков игнорируются только назначаемые хабом
`blockId` и runtime `if.state` на известных путях BLOCK-схемы; одноимённые поля
в неизвестных vendor-поддеревьях остаются конфигурацией. Неизвестные поля
существующего BLOCK должны быть сохранены без изменений. У API нет
compare-and-set, поэтому между последним чтением и записью остаётся явно
неустранимая гонка.

`preview_boolean_automation` принимает квалифицированные домом ссылки комнаты и
характеристики источника и цели. Запись пока поддерживается только для дома из
`SPRUTHUB_SERIAL`; ссылка другого дома отклоняется до запроса к хабу. Ранее
сохранённые неквалифицированные ссылки читаются только из локального журнала,
который уже привязан fingerprint к URL и serial. Необязательный
`auto_off_after_seconds` для
`MotionDetected=true` → `On=true` добавляет после немедленного включения один
нативный `RESET` delay с выключением. Каждый новый триггер начинает полный
отсчёт заново; отсутствие события не доказывает отсутствие человека. Preview
заново читает выбранные устройства,
сценарии, назначенные и доступные логики, связи, опции и установленные модули,
показывает конкретный нативный BLOCK и возвращает `change_ref`. Preview не
записывает данные в SprutHub, но сохраняет локальную историю подготовленного
изменения с причиной.

`apply_automation_change` по `change_ref` повторно проверяет ссылки, типы,
доступность и права. Эквивалентный поддерживаемый BLOCK переиспользуется даже
при другом имени, только если его `active`, `onStart` и `sync` также совпадают.
Иначе инструмент возвращает `conflict` и не включает чужой сценарий и не создаёт
дубликат. Если сценарий нужен, создаётся ровно один объект, после чего его
конфигурация читается и сравнивается. Потеря или несовместимость ответа после
отправки create сначала приводит к сверке хаба; неизвестный исход остаётся
`uncertain`, а повторный apply не отправляет create вслепую.

`get_automation_change` сверяет локальную запись с хабом после перезапуска MCP.
`rollback_automation_change` удаляет только объект с маркером этого изменения и
точно ожидаемой конфигурацией. Добавляемый SprutHub после исполнения
`data.targets[0].state` считается runtime-состоянием блока `if`, а назначаемые
редактором `blockId` — производными идентификаторами структуры; прочие поля,
`delay.index`, настройки и действия остаются частью точной защиты. Ручная
правка даёт `conflict` и сохраняется. Удаление сценария не возвращает уже
изменившееся физическое
состояние лампы.

Перед удалением инструмент сохраняет локальное намерение отката и не отправляет
delete, если это не удалось. После наблюдения хаба исход, владение и результат
финального сохранения считаются отдельно для apply, status и rollback. Поэтому
отказ финального журнала не заменяет подтверждённые `applied`, `rolled_back`,
`already_present` или `conflict`: ответ добавляет `local_state.saved: false` с
безопасным действием восстановления. Неустановленный исход остаётся `uncertain`
и не утверждает, что сценарий не был создан. После восстановления каталога
следует вызвать `get_automation_change`; этот read-only инструмент вычисляет
актуальный статус, не переписывая журнал.
Однозначный отказ хаба остаётся `request_rejected`, даже если обратный переход
журнала в `prepared` сохранить не удалось. В таком случае старый `change_ref` не
повторяют: после восстановления каталога выполняют новый preview.

Локальная история привязана к URL и serial настроенного хаба через SHA-256 и не
содержит token. По умолчанию она хранится вне Git в системном каталоге состояния
пользователя; `SPRUT_AGENT_STATE_DIR` задаёт другой каталог, например для
изолированного запуска. Preview не является атомарной резервацией между ним и
apply. Пустой прямой список сценариев не доказывает отсутствие зависимостей
внутри произвольного кода или bridge-модуля. Поддерживается один пишущий
MCP-процесс на хаб: внутри него apply и rollback выполняются последовательно.
Межпроцессной блокировки нет. В наблюдённом API нет conditional delete, поэтому
инструмент блокирует откат при уже прочитанной ручной правке, но UI или другой
процесс всё ещё может изменить сценарий после последней проверки и до удаления.

## Исследование протокола

| Команда | Результат |
| --- | --- |
| `npm run research:diff -- --from <снимок> --to <снимок>` | Сравнение схем и каталога операций двух снимков |
| `npm run research:record -- --cdp-url http://127.0.0.1:9222` | Пассивная запись WebSocket-событий из браузера через Chrome DevTools Protocol |
| `npm run research:snapshot` | Попытка извлечь схемы и метаданные из публичной сборки интерфейса |

Для записи нужна отдельная браузерная сессия с CDP и ручная авторизация
в SprutHub. После запуска recorder перезагрузи страницу; остановка — `Ctrl-C`.
Запись сохраняется в `research/captures/raw/` с правами `0600`, каталог исключён
из Git. Сырые записи могут содержать секреты; санитайзер пока не реализован.

**Границы совместимости.** Снимок `1.5.58` относится к сборке 2025-09-16.
Полный snapshot CLI не принят на текущей публичной сборке: ранее он остановился
на распознавании build. Отдельная функция извлечения protobuf-модулей успешно
прочитала текущий JS; нативные каталоги типов проверены на хабе.
[Источники и карта модели](research/protocol/2026-09-09-model.md) различают эти
проверки. Номер версии интерфейса сам по себе не подтверждает контракт хаба.

Нативные `room.list`, `room.get` и `accessory.list` с фильтром комнаты наблюдались
на Sprut.hub 2 с прошивкой `3.0.0b (20131)`. Источник и ограничения проверки —
в [записи от 2026-09-09](research/protocol/2026-09-09.md).

## Разработка

Продуктовые ожидания проверяем через публичные точки входа. Тесты recorder
запускают отдельный процесс и локальный CDP-сервер; тесты MCP —
настоящий MCP-процесс и внешний тестовый WebSocket-хаб. Подмена внешнего хаба
не заменяет живую приёмку SprutHub.

```sh
npm run check           # Обязательные проверки: Biome и офлайн-тесты
npm run test:mutations  # Необязательная диагностика настроенной области
```

Ручной сценарий неоднозначного выбора запускает новый диалог Codex с
синтетическим внешним хабом и печатает трассу инструментов и ответ:

```sh
node research/check-agent-room-ambiguity.mjs ambiguous
```

Доступны также режимы `office` и `ambiguous-distinct`. Сценарий требует Codex CLI
и сетевого доступа к модели, не входит в `npm test`; exit code подтверждает только
завершение запуска. Соответствие ответа критерию оценивается по напечатанному
ответу вручную.

Обычный CI выполняет быстрые проверки и commitlint. Качество принимаем по
продуктовым тестам, независимому ревью и живой проверке на хабе. Адресные мутации
помогают разобрать конкретное сомнение в тесте. Полный Stryker запускается только
как отдельная диагностика, локально или вручную в GitHub Actions; обязательного
порога mutation score нет. Область задана в [конфигурации](stryker.config.json),
результат относится только к ней. Правила выбора проверки — в [AGENTS.md](AGENTS.md).

`npm test` проверяет MCP-путь через официальный клиент, настоящий дочерний
stdio-процесс приложения и внешний локальный WebSocket-сервер. Сценарии
покрывают полный каталог и выбор по ссылке, значения, единицы, контекст сервиса,
повторное чтение, неполные ответы, авторизацию, общий deadline вызова, обрыв и
восстановление. Температуры и мультисенсор проверяются по обезличенным
проекциям наблюдённых ответов хаба. Это офлайн-доказательство контракта,
а не живая семантическая проверка агента или гарантия совместимости
со всеми версиями SprutHub.

Используем Conventional Commits и отдельные RED/GREEN-коммиты для изменений
поведения. Git hooks проверяют сообщение коммита и запускают `npm run check`
перед push. Полные правила, включая владение рабочей копией и её уборку, —
в [AGENTS.md](AGENTS.md); [CLAUDE.md](CLAUDE.md) ссылается на тот же файл.

[mcp_servers.plan]
url = "https://api-plan.nuanu.ai/mcp"

chmod 600 .codex/config.toml
