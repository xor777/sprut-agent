# sprut-agent

**Agent-first интеграция для умного дома на SprutHub.**

[![CI: GitHub Actions](https://img.shields.io/badge/CI-GitHub_Actions-24292F?logo=githubactions&logoColor=white)](https://github.com/xor777/sprut-agent/actions/workflows/check.yml)
[![Node.js 24+](https://img.shields.io/badge/Node.js-24%2B-417E38?logo=nodedotjs&logoColor=white)](package.json)
[![MIT License](https://img.shields.io/badge/License-MIT-2563EB)](LICENSE)

sprut-agent создаётся, чтобы поручать ИИ работу с домом: понимать устройства,
настраивать автоматизации и разбираться в их поведении. Интеграция даёт агенту
программный доступ к SprutHub; сам хаб остаётся местом исполнения сценариев.
Подробнее о целевом опыте — в [видении продукта](https://plan.nuanu.ai/project/SPRUT/docs/176).

> [!IMPORTANT]
> Проект на ранней стадии. Чтение проверено на настоящем SprutHub и с агентом.
> На целевом хабе с внешним агентом проверены создание и изменение BLOCK,
> повтор без дубля, восстановление в новом диалоге и сохранение чужой правки.
> Проверены команда лампе и один естественный цикл автоотключения.
> Повторное событие датчика внутри минуты ещё не подтверждено.
> Прямой вход по логину и паролю, сохранение сессии и повторный запуск проверены
> владельцем на настоящем SprutHub 2026-09-10 без передачи секретов агенту.

## Установка в Codex

Поддерживаемый путь рассчитан на установленный Codex CLI 0.154.0 или новее на
macOS arm64. Нужны Node.js 24+, npm, Git, доступ к GitHub и своему SprutHub.
Перед изменением профиля агент проверяет реальные предпосылки:

```sh
codex --version
node --version
npm --version
git --version
```

Новому агенту достаточно дать ссылку
`https://github.com/xor777/sprut-agent` и сказать: «Помоги установить sprut-agent
и подключить мой дом. Не проси меня передавать пароль в чат». Агент устанавливает
единый комплект MCP и skill штатными командами Codex:

```sh
codex plugin marketplace add https://github.com/xor777/sprut-agent.git --ref main
install_result="$(codex plugin add sprut-agent@sprut-agent --json)"
installed_path="$(node -p 'JSON.parse(process.argv[1]).installedPath' "$install_result")"
node "$installed_path/check-install.mjs" "$installed_path"
```

Последняя команда проверяет именно выбранный Codex transport, runtime и skill из
установленной копии, а не исходный checkout. Если имя MCP `sprut-agent` уже занято
другой настройкой, проверка сохраняет её и объясняет продолжение. Удаляй такую
запись через `codex mcp remove sprut-agent` только после подтверждения, что она
больше не нужна; затем повтори установку plugin и проверку.

У прежнего пользователя может остаться пара из ручного MCP `sprut` и
пользовательского skill `spruthub-master`. Проверка находит активные skills через
Codex и не сообщает готовность, пока прежний skill может направить новый диалог к
старому MCP. Для обнаруженного прежнего skill она печатает одну точную команду с
его путём. Агент выполняет её только после сопоставления с прежней ручной
установкой: штатная настройка Codex отключает этот skill, не удаляя симлинк, его
target, старый MCP или соседние настройки. После этого агент повторяет проверку.
Произвольный одноимённый skill молча не отключается.

Если навык плагина был отдельно отключён в Codex, включи его штатной настройкой
навыков: повторная установка плагина не отменяет это отключение. Для диагностики
используй вывод проверки или `codex mcp get sprut-agent`, который маскирует
значения переменных окружения.

После успешной проверки агент безопасно готовит локальный файл, но логин и
пароль владелец вводит в него сам локально, не в чат:

```sh
mkdir -p "$HOME/.config/sprut-agent"
chmod 700 "$HOME/.config/sprut-agent"
touch "$HOME/.config/sprut-agent/connection.env"
chmod 600 "$HOME/.config/sprut-agent/connection.env"
```

Содержимое `connection.env`:

```dotenv
SPRUTHUB_LOGIN=ваш_логин
SPRUTHUB_PASSWORD=ваш_пароль
```

После сохранения файла начни новый диалог и спроси: «Какая сейчас температура в
офисе?». При одном доступном доме агент выберет его явно; при нескольких
попросит уточнить дом.
Успешный вход сохраняет сессию рядом с настройкой, поэтому следующий запуск не
требует пароль повторно. Эти файлы и журнал изменений находятся вне кэша plugin
и сохраняются при повторной установке.

Шаги установки можно безопасно повторить. Если процесс прервался после
добавления marketplace, повтори их с начала: Codex продолжит без дубля и не
перезапишет соседние MCP-настройки. Неверные реквизиты исправляются только в
`connection.env` с последующим новым запуском; переустановка не нужна. Ошибка
`authentication_failed` означает отказ в реквизитах, а `connection_failed` —
недоступность хаба, не поломку установки.

Plugin запускает готовый локальный bundle из собственного кэша и не выполняет
`npm install` или сетевую загрузку при старте MCP. Установка по Git-ссылке и
переход с прежнего ручного комплекта проверены свежим агентом на macOS arm64
с Codex CLI 0.154.0: локальный ввод реквизитов, один новый диалог и правильный
ответ о доме. Эти агентные проверки использовали синтетические хабы.
Из установленного bundle отдельно проверены вход, чтение настоящего SprutHub
и повторный запуск с сохранённой сессией. Повтор установки и продолжение после
прерывания проверены в отдельных профилях, без изменения настроек владельца.

## Что есть сейчас

| Часть | Возможности | Готовность |
| --- | --- | --- |
| Подключение | Нативный вход по логину и паролю из локального файла; получение домов и сохранение сессии | Вход, чтение дома и повторное использование сессии после перезапуска проверены на настоящем хабе |
| Исследование протокола | Извлечение схем, сравнение снимков, пассивная запись WebSocket-трафика | Доступно в `main`; ограничения extractor описаны ниже |
| MCP-интеграция | Выбор доступного дома, byte-bounded обзор сервисов комнаты или дома и адресное чтение нативных сущностей и настроек по устойчивой ссылке | Базовое сквозное чтение проверено на живом доме; обзор, native-фильтр, scope и cursor проверены офлайн на наблюдённой форме данных |
| Размещение устройств | Переименование и перенос выбранного аксессуара, создание отсутствующей комнаты, поиск и возврат собственных изменений в новом диалоге | Перенос, нормализация имени и возврат проверены через MCP на реальной лампе; свежие агенты проверили создание комнаты и сохранность соседей на независимом стенде |
| Автоматизация | Preview и идемпотентное применение boolean → boolean BLOCK; подготовка, применение, сверка и защищённое восстановление ограниченных нативных изменений, включая одну настройку физического окна, назначаемую logic и source собственного LOGIC | BLOCK/property, `window_option` и назначение/настройка/активация logic проверены через MCP на целевом хабе; LOGIC source CRUD, SDK, история и защита возврата проверены офлайн на native-shaped границе и ещё требуют живой приёмки |
| Наблюдения на хабе | Агент читает температуры и параметры мультисенсора; MCP получает обновления при повторном чтении и восстанавливает связь | Проверено на одном Sprut.hub 2; это не гарантия совместимости со всеми версиями |
| Нативные события | Ограниченное наблюдение выбранных характеристик, исполнения и нативного журнала одного сценария с явным статусом, сроком и уборкой подписок | Native transport, формы событий и журнала подтверждены на целевом хабе; фильтрация, повторы, разрыв и завершение проверены офлайн через публичный MCP |
| Программное чтение | Публичный read-only API возвращает выбранные характеристики одного дома с единицами, enum, доступностью и свежестью | SDK прочитал настоящий дом; повторное значение, отдельная ошибка источника и закрытие соединения проверены через собранный plugin |

Пример рабочего сценария MCP — вопрос «Какая температура в офисе?».
Агент сначала получает доступные дома, явно выбирает дом, затем получает исходные
названия комнат и читает через `read_services` компактную целую картину выбранной
комнаты. Для известного native типа тот же инструмент ищет совпадения по дому без
ручного обхода комнат. Только контракт или настройки выбранного прибора агент
раскрывает через `get_entity`.
Смысл запроса разбирает агент; интеграция отвечает за идентификаторы, значения,
единицы и свежесть.

## Наблюдать нативные события автоматизации

Для разбора паузы или повторного запуска агент сначала выбирает один `home_ref`,
точные event-capable characteristic refs и ref существующего сценария. Затем
`start_native_observation` запускает ограниченное наблюдение и сразу возвращает
`observation_ref`; `get_native_observation` показывает накопленные события и
статус, а `stop_native_observation` досрочно завершает операцию. По умолчанию
наблюдение длится 180 секунд, максимум — 300 секунд и 500 событий. За один
MCP-процесс выполняется одно наблюдение; его результат хранится до следующего
успешно начатого наблюдения или завершения процесса. Наблюдение использует
отдельное соединение выбранного дома, поэтому во время него обычные `list_homes`,
`inspect_home`, `get_entity` и `read_services` остаются доступны и не меняют область
собираемых событий.

Такой двухшаговый вызов не держит один MCP request несколько минут. Ожидание в
`get_native_observation` ограничено 20 секундами, но само наблюдение продолжается
до срока, лимита, разрыва связи или явной остановки. Результат сохраняет порядок,
повторные значения, типизированное значение, native scenario `type`/`blockId` и
точно относящиеся к выбранному индексу сообщения журнала исполнения. Для журнала
сохраняются исходный `message`, `level`, `path`, native `time_ms`, вычисленный из
него `source_timestamp` и отдельное локальное `received_at`; текст журнала —
недоверенные данные, а не доказанная причинность. Characteristic/scenario event
не содержит времени источника и home ID: дом задаётся выделенным на время
наблюдения соединением. Частичный characteristic frame не заменяет полный state,
а близкие времена событий не доказывают причинность или физический эффект. При
завершении освобождаются обе подписки. Статусы `connection_lost`, `truncated` и
`canceled` явно означают неполное окно.

## Программно читать выбранные показатели

Для собственного Node-приложения импортируй
`createSprutHubReader` из `$installed_path/dist/read.mjs`. Его единственная
операция `read({ homeRef, readings: [{ ref, label }] })` принимает характеристики
одного явно выбранного дома и возвращает только выбранные безопасные значения,
их native type, единицы, enum, доступность и времена чтения/измерения. Закрой
созданный reader при остановке приложения. Reader использует тот же локальный
credential-профиль, что и MCP; логин, пароль, token и session не передаются в подборке показаний.
Write-операций этот entry не экспортирует.

## Что можно изменить в доме

Нативный write-path умеет менять одно типизированное значение характеристики,
один доступный для записи `GenericInteger/LIST` option физического окна с явными
вариантами, назначать доступный сервису native logic, менять её `active` и один
доступный для записи `GenericInteger/NUMBER` option, создавать BLOCK в
опубликованном ограниченном формате и полностью заменять `data` существующего
BLOCK, а также создавать собственный сценарий `LOGIC` с безопасным
ownership-комментарием в отправленном JS и точно менять его source. Актуальные
декларации sandbox доступны отдельно через
`get_scenario_sdk`; код локально не исполняется и не анализируется. Каждое
изменение сначала сохраняет baseline и diff, а после отправки отдельно сообщает
ACK и readback. Создание GLOBAL, pairing, backup и бесконечный сбор native events
не реализованы.
Специализированный `MotionDetected=true` → `On=true` preview остаётся доступен и
может добавить автоотключение через заданное число секунд.

Штатное плавное включение проверено на `SmoothBrightnessChange`; настройка и
возврат через MCP сохраняют остальные параметры и назначения. Источник протокола,
наблюдения и границы проверки — в [журнале исследования](research/protocol/2026-09-10-native-logic.md).
Физическая плавность глазами владельца не проверялась.

## Из чего состоит проект

Один пакет на JavaScript, Node.js и npm. У исследовательских инструментов
самостоятельные команды; MCP-сервер запускается одним процессом.

| Компонент | Зачем нужен |
| --- | --- |
| [MCP-сервер](src/server.mjs) | Предоставляет агенту чтение нативной модели дома и инструменты автоматизации; использует официальный MCP SDK и Zod |
| [Подключение к SprutHub](src/spruthub-connection.mjs) | Выполняет нативный вход, проверяет полученную сессию и сохраняет её локально для следующего процесса |
| [Клиент SprutHub](src/spruthub-client.mjs) | Выполняет узкий набор нативных запросов через WebSocket, преобразует ответы и ошибки хаба |
| [Исследовательские утилиты](research/) | Помогают наблюдать протокол и находить изменения между сборками интерфейса |
| [Журнал протокола](research/protocol/) и [снимки](research/snapshots/) | Сохраняют источники, версии и границы подтверждённого поведения |

Путь запроса:

```text
ИИ-агент → MCP по stdio → sprut-agent → JSON-RPC по WebSocket → SprutHub
```

Основной путь работает через протокол хаба и не зависит от расположения кнопок
в интерфейсе. Изменения самого протокола всё ещё могут потребовать обновления
клиента — поэтому наблюдения и проверка на конкретной версии входят в работу.

## Найти дом и прочитать нативный объект через MCP

Основной read-only путь начинается с `list_homes`: инструмент возвращает дома,
доступные учётной записи, а при единственном результате указывает его как выбор
по умолчанию. `inspect_home` принимает явный `home_ref` и раскрывает небольшой
каталог комнат, сценариев и расширений. `get_entity` читает выбранную комнату,
устройство, сервис, характеристику, сценарий, расширение, назначенную логику или
окно физических настроек. Опции, связи, физическая конфигурация и объёмная
диагностика раскрываются только через `include`. `include` применяется к
указанной сущности, а не рекурсивно ко всем её детям. Безопасная характеристика
возвращает `option_scope`: нативную доступность options как `true`, `false` или
`null`, состояние фактического чтения и точный следующий вызов. Только реальный
совместимый ответ `characteristic.getOptions` с явным массивом даёт `found` или
`checked_empty`; отсутствующий или неверный operation container возвращает
`incompatible_response`, а не пустой результат. В полном результате каждый
запрошенный include перечислен в `include_resolution.applied` или `not_applied`;
в ограниченном обзоре этот раздел остаётся отдельной адресной частью. Для
неприменимого include ответ даёт следующий исполнимый вызов по безопасной
возвращённой ссылке, когда такая ссылка известна, иначе явно сообщает
ограничение. Отсутствие массива не означает, что все дочерние области проверены.
Физическое окно и назначенная логика остаются отдельными владельцами настроек.
Terminal redacted marker не получает `include_resolution` и не раскрывает ссылки.

`get_entity` ограничивает компактный сериализованный ответ параметром
`max_bytes` (по умолчанию 16 000 UTF-8 байтов). `representation.kind` явно
различает `complete_entity`, `entity_overview` и `selected_value`: только полный
вариант содержит `entity`, а обзор и выбранная часть — отдельную `identity`.
Поэтому непрочитанная конфигурация не выглядит отсутствующей. Карта
`available_parts` содержит безопасные key/name/type/ref/kind дочерних объектов и
готовые вызовы с RFC 6901 `pointer`, исходными `entity_ref` и `include`. По ней
можно выбрать одну настройку или service до чтения значения. Версионный `next`
карты обнаруживает изменение порядка/identities. Для элемента с уникальным
непустым `ref` или `key` обычное изменение текущего значения не устаревает карту;
при отсутствующей или повторяющейся устойчивой identity версия консервативно
учитывает весь нормализованный и уже скрытый элемент. Такой `next` может чаще
дать `stale_entity_content`, зато не продолжает чтение по сместившимся элементам.
Длинная строка возвращается точными частями с позициями в Unicode-символах;
продолжение без версии отклоняется, а изменившаяся, укороченная или пустая строка
даёт `stale_entity_content` и вызов с начала.
Завершение последней строковой части не означает, что этот ответ содержит всю
строку или сущность. Проекция выполняется после нормализации и скрытия секретов;
redacted marker остаётся терминальным, а отсутствующий или несериализуемый
pointer даёт отдельную ошибку.

У сценария `include=configuration` всегда один payload в `configuration.value`.
`format=json` означает декодированное и санитизированное native JSON-значение,
`code` — точный redacted source с `content_origin`, `invalid_json` — точный
redacted native-текст, а `not_returned` — `null`. Формат отличает отсутствующие
данные от пустой строки и возвращённых JSON `false`, `0` или `null`.

`read_services` принимает обязательный `home_ref`, необязательные `room_ref` и
точные native `service_types`, а также лимит сериализованных UTF-8 байтов. Ответ
сохраняет исходные room/accessory/service refs и имена, доступность, читаемые
значения, единицы, enum и честную свежесть. Пустая область, отсутствие совпадений
и ошибка хаба различаются. Для продолжения выполняй готовый `next` до `null`;
при `invalid_cursor` или `stale_cursor` он безопасно начинает ту же область
заново. Страницы читаются заново и не обещают атомарный снимок меняющегося дома.
Детальный контракт, logic и options остаются в адресном `get_entity`.

Для назначенной logic наблюдённый ответ `logic.getOptions` с существующим пустым
operation container означает известный пустой список options. Отсутствующий
container, `null` или не-массивное значение options остаются несовместимым
ответом.

Все новые ссылки квалифицированы домом: `spruthub://hub/<serial>/room/<id>` и
`spruthub://hub/<serial>/accessory/<aId>/service/<sId>/characteristic/<cId>`;
serial кодируется как компонент URI. Поэтому одинаковые локальные ID двух домов
не смешиваются. Код и диагностический текст сценариев и устройств возвращаются
как недоверенные данные. Распознанная credential/PASSWORD-сущность целиком
заменяется явным redacted marker, включая её значения, потомков и native
identifier. Свободный текст с известным credential-представлением скрывается
целиком; произвольный секрет невозможно распознать математически полно.
В JavaScript эвристика покрывает распознанные именованные присваивания и
текстовые пары; сравнения, вызовы, вычисленные и закодированные значения могут
остаться нераспознанными.
Классификация выполняется по исходным native metadata до построения публичного
ответа. В `read_services` и `get_entity` marker остаётся отдельным терминальным
значением, поэтому обычные соседние показания остаются доступны:
`include` не раскрывает его потомков и не запускает дополнительные чтения.
Если точное значение текущего connection token встречается в JSON-key,
скрывается только ближайший содержащий этот ключ объект.

`list_rooms` использует дом по умолчанию и возвращает квалифицированные ссылки
для `read_services` и `get_entity`. Агент сопоставляет слова пользователя с
каталогом; поиск по имени внутри интеграции не выполняется.

Breaking change: прежний MCP-инструмент `read_room` удалён из предлагаемой
агенту поверхности. Обзор комнаты выполняется только через ограниченный по
размеру `read_services`; программный reader использует адресный `get_entity`.

Результат чтения сохраняет ссылки комнаты, устройств, сервисов и характеристик,
контекст сервиса, доступность, значения и единицы. Для нативного перечисления
рядом с исходным значением возвращается `enum` с ключом и названием; неизвестный
код остаётся исходным значением с `enum: null`. В `readings` попадают только
характеристики, которые хаб явно пометил доступными для чтения. Пустой `devices` означает существующую пустую комнату.
Неверная, устаревшая или относящаяся к другому дому ссылка даёт
структурированную ошибку с предложением снова вызвать каталог.

Настрой подключение локально. Владелец хранит только логин и пароль в файле вне
репозитория; значения не должны попадать в Git, логи или ответы инструмента:

```sh
mkdir -p "$HOME/.config/sprut-agent"
touch "$HOME/.config/sprut-agent/connection.env"
chmod 700 "$HOME/.config/sprut-agent"
chmod 600 "$HOME/.config/sprut-agent/connection.env"
```

Содержимое `~/.config/sprut-agent/connection.env`:

```dotenv
SPRUTHUB_LOGIN=owner@example.com
SPRUTHUB_PASSWORD=local-secret
```

Штатный `npm start` и прямой запуск сервера сами читают этот файл. После его
создания перезапусти то же MCP-приложение; менять уже настроенные command, args
или env не нужно:

```sh
npm start
```

По умолчанию используется beta endpoint `wss://beta.spruthub.ru/spruthub`.
Для другого сервера добавь `SPRUTHUB_URL` в тот же файл. После нативных шагов
`account.auth` и `account.answer` полученная сессия проверяется через `hub.list`
и атомарно сохраняется в `~/.config/sprut-agent/session.json` с режимом `0600`.
Следующий процесс сначала проверяет эту сессию и входит заново только при
подтверждённом отказе авторизации. Путь можно изменить через
`SPRUT_AGENT_SESSION_FILE`.

Прямой вход из локального файла, чтение температур и повторное чтение новым
MCP-процессом с сохранённой сессией проверены на настоящем SprutHub 2026-09-10.
Разделение чтения и записи между несколькими домами проверено офлайн;
это не живая проверка нескольких хабов.

Если переменных нет, любой публичный инструмент возвращает ошибку
`configure_credentials`. Основное сообщение и `credential_setup` содержат
абсолютный путь текущего профиля, обязательные поля, права `0600` и просьбу
перезапустить то же MCP-приложение. Логин и пароль всё равно создаются владельцем
локально: их нельзя передавать агенту в чате. Полный явно переданный профиль —
логин с паролем либо token с URL и CID — не читает default `connection.env`,
поэтому значения другого профиля и состояние этого файла на него не влияют. При
неполном профиле явно переданные процессу `SPRUTHUB_*` значения имеют приоритет
над файлом; из файла читаются только поддержанные параметры подключения,
остальные ключи не применяются к процессу. Явное пустое значение файл не
заменяет. Нечитаемый, не обычный или доступный другим пользователям файл, когда
он нужен, даёт исправимую ошибку `credential_file_unavailable`, а не
притворяется отсутствующим.

Если учётной записи доступен один дом, он безопасно выбирается для операций без
квалифицированной ссылки. При нескольких домах `list_homes`, `inspect_home`,
`get_entity` и `read_services` позволяют явное чтение по home-qualified ref, но это
не становится неявным выбором для будущей записи. Для `list_rooms` и всех
операций автоматизации добавь явный `SPRUTHUB_SERIAL`; без него сервер вернёт
`home_selection_required` до записи.

Ранее настроенный путь с готовой сессией остаётся доступен: укажи
`SPRUTHUB_URL`, `SPRUTHUB_TOKEN`, `SPRUTHUB_SERIAL` и `SPRUTHUB_CID` вместо
логина и пароля. `SPRUTHUB_TIMEOUT_MS` необязателен; по умолчанию весь вход или
один обычный запрос ждёт не более 10 секунд. CAPTCHA, подтверждение по коду,
регистрация нового пароля, выбор хаба внутри auth-flow и перенаправление не
угадываются: сервер останавливается с исправимой структурированной ошибкой.

`freshness.hubResponseReceivedAt` — локальное время получения полного ответа
хаба. `measurementAt: null` означает, что подтверждённое время самого измерения
не получено; время ответа не выдаётся за время измерения. Каждый вызов читает
данные заново. После временной ошибки можно повторить тот же инструмент в том же
MCP-сеансе; успешный старый ответ не кэшируется. В нативной модели
`source_timestamp: null` означает, что SprutHub не вернул время источника.
Настроенное значение, диагностика устройства и `pending: "unknown"` остаются
разными фактами и не выводятся друг из друга. В этом срезе адаптер не связывает
HTML-диагностику с option: ни суффикс native key, ни совпадение имени свойства не
дают полной общей identity, поэтому structured `reported_value` остаётся `null`.
Безопасная диагностика доступна отдельно через `include=diagnostics`.

Ссылка расширения строится только из непустого native `extensionKey`. Отсутствие
или конфликт этого ID даёт `incompatible_response`, а не alias из общего `type`.

`inspect_home.coverage` перечисляет только операции, завершившиеся в этом
вызове; успешный `list` не подтверждает `get` или `window.get`. Неподдержанный
метод (`-32601`), отказ доступа и отсутствие ответа различаются как
`unsupported`, `insufficient_access` и `unknown`. Строковый native `owner`
сохраняется отдельно, а право ownership без boolean-доказательства остаётся
`unknown`.

Read-only envelope `room.list`, `room.get` и фильтрованный по `roomId`
`accessory.list` наблюдались 2026-09-09 на Sprut.hub 2 с прошивкой
`3.0.0b (20131)`; обезличенный источник и границы — в
[`research/protocol/2026-09-09.md`](research/protocol/2026-09-09.md).
В новом диалоге Codex проверен путь «офис» → каталог → выбранная комната →
обе температуры настоящего хаба. В отдельной живой проверке разрыв соединения
интеграции дал исправимую ошибку, а следующий вызов в том же MCP-процессе
восстановил чтение. Инструменты чтения ничего не записывают в дом.

Расширенный путь `list_homes` → `inspect_home` → `get_entity` проверен на том же
хабе: комнаты, физические настройки датчика, назначенные логики, разные экземпляры
расширений и конфигурации BLOCK/GLOBAL. Свежий Codex gpt-5.6-terra/medium прочитал
настоящий BLOCK и объяснил отсчёт таймера от события хаба, сохранив неопределённость
относительно последнего физического движения. Это один проверенный запрос,
а не оценка готовности агента ко всем задачам дома. Доказательства и ограничения —
в [приёмке модели дома](https://plan.nuanu.ai/project/SPRUT/issue/18).

На настоящем мультисенсоре физическое изменение освещённости дважды дало новое
значение с прежней ссылкой характеристики; источник и границы — в
[наблюдении от 2026-09-09](research/protocol/2026-09-09-motion.md). Позднее
переход движения `false → true` запустил созданный BLOCK и физически включил
целевое устройство; свидетельство — в
[исследовании автоматизаций](research/protocol/2026-09-09-automations.md).
В отдельных синтетических диалогах агент
сохранил исходные имена двух подходящих офисов при одинаковых и разных
показаниях, но эти примеры не гарантируют поведение любой модели и формулировки.
На этом же мультисенсоре сопоставлены все 16 читаемых характеристик; новый
диалог агента правильно объяснил нативные состояния разряда и зарядки.

## Preview, применение и откат автоматизации

Для общего нативного изменения сначала вызови `get_native_change_contract`,
затем `prepare_native_change` и проверь сохранённые baseline и diff. Поддержаны
операции `accessory_placement`, `room_create`, `virtual_light_group`,
`characteristic_value`, `window_option`, `block_create`, `block_data_update` и
`block_action_pause`, а также
`logic_assignment`, `logic_active`, `logic_option`, `logic_source_create` и
`logic_source_update`;
`block_data_update` заменяет только полное `data`, не имя и
runtime-флаги сценария. Для `window_option` передай ref прочитанного физического
окна и точный `option_key`; контракт возвращает допустимые значения. Уже
установленное значение даёт `already_desired` без записи и без фиктивного
собственного change.
`accessory_placement` принимает ref одного accessory, точный существующий
`room_ref` и новое имя. Он отправляет только имя/комнату выбранного accessory,
показывает requested и сохранённое после пустого ACK имя и не затрагивает
services или соседние accessories общего физического устройства. Если комнаты
нет, `room_create` выполняется отдельным change; его ref затем используется для
размещения. Потерянный ответ create не вызывает повтор: новые одноимённые комнаты
возвращаются как кандидаты без права удаления. Если свежий каталог подтверждает,
что комната не появилась, прежний change остаётся неопределённым, а новый
`room_create` повторно проверяет отсутствие перед записью. Возврат выполняется в
обратном порядке — сначала accessory, затем только подтверждённо собственная,
неизменённая и пустая комната. Создание/удаление комнаты подтверждено официальными
frontend и protobuf-схемой, но ещё не проверено live-записью.
Если ответ обновления потерян, а хаб нормализовал имя, наблюдённых данных может
не хватить для установления собственного изменения: оно остаётся `uncertain`
без автоматического возврата. После сверки фактического состояния исходные
имя и комнату можно задать новым разрешённым `accessory_placement`.
`virtual_light_group` принимает точную комнату, не менее двух прочитанных
`Lightbulb` service refs и явный общий набор `On`, `Brightness`. Подготовка
проверяет эти характеристики у каждого участника и текущий `service.types`, но
ничего не пишет. Применение создаёт один нативный виртуальный `Lightbulb`,
добавляет входящие links к выбранным характеристикам, включает их и проверяет
эффективный `linkProcessing=0` (`LastValue`): ручное изменение одной лампы
обновляет обратную связь группы, но не должно автоматически синхронизировать
остальные.
Ответ create задаёт принадлежащий change ID; если хаб нормализовал имя, результат
отдельно показывает requested и observed name вместо потери владения.
Температура цвета или служебная характеристика одной лампы в группу не попадает.
Повтор проверяет accessory и links и не создаёт их заново. Потерянный ответ
отдельного link восстанавливается чтением; потерянный ответ создания показывает
не-владельческий кандидат и не повторяет create. Возврат после рестарта удаляет
только подтверждённо созданный виртуальный accessory, пока его структура и links
не изменены вручную. Сначала он удаляет IN-links с виртуальной характеристики тем
же путём, что текущий UI; потерянный после `addVirtual` readback восстанавливается
по свежей IN-связи и member ref. Непосредственно до и после удаления инструмент
проверяет, что SYSTEM и чужие consumers сохранены, затем выключает `hasLinks` и
удаляет accessory. Исчезновение чужой связи до начала возврата не блокирует
удаление своей группы. Сохранённая пара снимков до/после собственного удаления
не заменяется более поздним состоянием дома; если снимок после операции не был
получен, возврат завершается только когда сохранять было нечего либо все чужие
связи видны свежим чтением. Их позднее отсутствие остаётся `uncertain`, а не
приписывается своей операции. Если отправка удаления потеряна до хаба, следующий
вызов возврата может повторить её после свежего подтверждения той же собственной
IN-связи с сохранённым ID. На связь отправляется не более одного удаления за вызов;
явный отказ хаба не блокирует следующую попытку. Связь с изменённым ID не удаляется.
Оставшийся собственный consumer либо
подтверждённая пропажа чужой связи во время операции оставляют change в
`uncertain`; новый пустой OUT-дескриптор
указывается в `native_link_residues`, но не выдаётся за действующую связь.
Физические участники не удаляются и не переписываются.
Формы create/link и `LastValue` подтверждены текущими официальными frontend,
protobuf-схемой и Wiki; источник и границы сохранены в
[наблюдении виртуального света](research/protocol/2026-09-11-virtual-light-group.md),
существующая группа прочитана на настоящем хабе. На hub 3.0.0 подтверждены
создание с возвращённым ID и обрезанием длинного имени до 30 символов, четыре
`addVirtual` и управление обеими лампами новым значением. Live-опыт также
установил важное ограничение: после ручного расхождения повтор уже отображаемого
виртуального значения может получить ACK, но не дойти до второго участника.
Команда через созданную продуктом группу поэтому читает каждого известного
участника и возвращает `uncertain/group_members_not_converged`, а не объявляет
успех по одному virtual scalar. Нативного подтверждённого способа принудительно
повторить такое же значение пока нет. Офлайн-тест подтверждает payload, журнал и
защиту восстановления; новый порядок удаления links ещё требует адресной live-
проверки.
Сервис через `get_entity` раскрывает назначенные logic и каталог доступных типов.
Перед написанием кода `get_scenario_sdk` возвращает полные текущие декларации
именно выбранного хаба, их размер, SHA-256 и свежесть. `logic_source_create`
принимает точный Lightbulb service ref, source и явные `name`, `description`,
`active`, `on_start`, `sync`. После create инструмент читает сценарий и заново
читает `logic.types`. Точный source считается применённым независимо от mapping;
`logic_mapping_status` и `logic_assignment_ready` отдельно показывают готовность
назначения. `type` определяется только по единственному новому элементу каталога,
а не из `scenario.index`. При `missing`/`ambiguous` собственный source остаётся
доступен для исправления через `scenario_ref`, но его удаление блокируется до
подтверждённого mapping, чтобы не пропустить назначение на другом сервисе.
Нормализованные хабом create flags возвращаются как `observed` рядом с
`exact_match`; именно наблюдённый снимок затем защищает ручные изменения.
Потерянный ответ сверяется по собственному маркеру и не вызывает второй create.
`logic_source_update` отправляет только `{index,data}` и отдельным readback
проверяет точный source. Возвращённые хабом metadata, включая заново выведенные
из JS `name` и `description`, сохраняются как наблюдённый снимок; перед отменой
полный снимок защищает последующую ручную правку, а readback отмены подтверждает
точный исходный source и фактические metadata. Инструмент не приписывает их
изменение source или параллельной правке: у SprutHub нет CAS. Predefined source
остаётся только для чтения и клонирования. Change-ответ выводит SHA-256, не
копируя сохранённый код из журнала. Это подтверждает сохранённую конфигурацию,
но не исполнение callback или физический эффект.

Неназначенный тип имеет готовый logic ref; новое назначение создаётся неактивным.
После этого прочитай logic с `include=options`, отдельно настрой нужные числовые
options и только затем активируй её. Это последовательность нативных операций, а
не атомарная транзакция. Повторное назначение и уже нужные значения дают no-op.
`apply_native_change` сохраняет намерение перед отправкой, отдельно возвращает
его направление apply/restore, нативный ACK и результат повторного чтения.
Перед новой отправкой инструмент заново проверяет native contract, bindings и
конкретные значения. При `uncertain` сначала вызови `get_native_change`: только
свежий baseline после неисполненной записи `window_option` позволяет следующему
авторизованному `apply_native_change` повторить её, не создавая новую историю.
`verification.fresh=false` явно означает, что новый readback не получен;
сохранённый исход операции и прежние различия конфигурации от этого не становятся
свежим доказательством.
`restore_native_change` возвращает сохранённый baseline окна, logic option,
`active`, LOGIC source или BLOCK только пока текущее значение совпадает с применённым; третье
значение сохраняется как conflict. Созданное назначение удаляется последним и
только если параметры и `active` возвращены к сохранённой созданной конфигурации.
При восстановлении BLOCK исходный снимок повторно проверяется по текущему
контракту: например, сохранённый delay с `index=0` отклоняется без записи в хаб.
Для option conflict показывает текущее, применённое и исходное значения и эффект
нового явно разрешённого изменения; сам conflict ничего не записывает.

`block_action_pause` принимает ref существующего BLOCK, RFC 6901
`action_pointer` на выбранное исполняемое действие/ветку и положительную
`duration_seconds`. При первом apply инструмент сохраняет абсолютный срок до
нативной записи и оборачивает только выбранный узел в `if` с code-condition
`return Date.now() >= <срок>`; исходный узел остаётся в `then`, а `else` пуст.
Поэтому после срока действие снова доступно на следующем обычном триггере без
живого MCP-клиента; пропущенные события не проигрываются в момент срока.
`pause_effect.status` отделяет `active`/`expired` от сохранённого статуса
конфигурации, а история показывает `effect_status` без чтения и записи хаба.
Повтор того же change после потерянного ответа не продлевает окно; подтверждённо
отклонённую запись можно повторить до того же сохранённого срока, а после
истечения она остаётся `not_applied` и больше не отправляется.
Новая пауза при выборе собственной обёртки или её непосредственного `then/0`
заменяет окно без вложения; старый change сразу получает `superseded` и не
оживает после restore нового. Собственный marker, точная форма и срок доказывают
владение независимо от сдвига узла соседней правкой; эквивалентное кодирование
ref не создаёт другую историю. Более узкий или широкий пересекающийся выбор
отклоняется с адресами существующей паузы. Подграф с `trigger=true` нельзя
оборачивать до подтверждения вложенной регистрации trigger; ошибка предлагает
исполняемые действия ниже него. Самостоятельное действие без trigger доступно.

Restore снимает только найденный неизменённый управляющий контейнер и сохраняет
текущее содержимое его `then`, включая ручную правку. Изменённый, неизвестный или
дублированный marker остаётся conflict. Истёкшая собственная обёртка инертна и
автоматически схлопывается в следующем подготовленном обычном
`block_data_update` этого сценария; после подтверждённой записи пауза получает
терминальный `completed`, а read-only вызовы скрытых записей не делают. Restore
обычной правки сохраняет неизменённую активную паузу, но не возвращает из её
baseline уже истёкшую, завершённую или заменённую обёртку. Если обычная
авторизованная правка явно убрала точный собственный контроллер, пауза получает
`restored`, а не ложный конфликт. Native update сценария может отменить уже
запущенную задержку прежней версии.
`active`/`expired` в MCP оценивается по локальным часам; само условие исполняется
по часам хаба, и синхронность этих часов не доказана.
Подготовленное или подтверждённо отклонённое изменение остаётся `not_owned` и не
получает права отменять совпавшую ручную настройку или чужое назначение.
Если собственное назначение после подтверждённого создания достоверно исчезло,
change навсегда теряет право на этот service/type: совпавшее назначение, которое
позже создал владелец, возвращается как conflict и не удаляется.
Созданный LOGIC удаляется только после отсутствия его фактически наблюдённого
type во всех текущих назначениях дома. Ручная правка source/flags и любое такое
назначение дают conflict без update/delete; между последней проверкой и записью
остаётся неустранимая гонка без native compare-and-set.
Завершённый `restored` терминален для этого change ref, а значение
физической характеристики инструмент не откатывает. `list_native_changes`
находит по дому и необязательной canonical entity ref окно, сценарий и
участвующие accessory/service/characteristic, включая старые записи automation
API. Его `recorded_status` —
сохранённый исход на `updated_at`, а не текущая проверка хаба; для неё вызови
возвращённый `next`. Обнаружение записи в истории не является разрешением на её
восстановление.

BLOCK-контракт версии `2026-09-10` допускает корневой `targets`, вложенные `if`
в режиме `EVERY`, условия `AND`/`OR` и типизированные characteristic comparisons,
действия service/set и delay `RESET` с уникальным положительным целочисленным
`index`. Нативные `aId/sId/cId` и типы проверяются
по выбранному дому. При сравнении снимков игнорируются только назначаемые хабом
`blockId` и runtime `if.state` на известных путях BLOCK-схемы; одноимённые поля
в неизвестных vendor-поддеревьях остаются конфигурацией. Неизвестные поля
существующего BLOCK должны быть сохранены без изменений. У API нет
compare-and-set, поэтому между последним чтением и записью остаётся явно
неустранимая гонка.

Для `window_option` ACK `window.update` не содержит итогового значения, поэтому
успех подтверждается только отдельным `window.get`. Прочитанное значение
доказывает сохранённую настройку хаба, но не доставку до физического устройства
и не поведение после реального отключения питания. BUTTON, disabled, read-only и
прочие типы controls этим путём не записываются.

`preview_boolean_automation` принимает квалифицированные домом ссылки комнаты и
характеристики источника и цели. Запись пока поддерживается только для дома из
`SPRUTHUB_SERIAL`; ссылка другого дома отклоняется до запроса к хабу. Ранее
сохранённые неквалифицированные ссылки читаются только из локального журнала,
который уже привязан fingerprint к URL и serial. Необязательный
`auto_off_after_seconds` для
`MotionDetected=true` → `On=true` добавляет после немедленного включения один
нативный `RESET` delay с выключением. Каждый новый триггер начинает полный
отсчёт заново; отсутствие события не доказывает отсутствие человека. Preview
заново читает выбранные устройства,
сценарии, назначенные и доступные логики, связи, опции и установленные модули,
показывает конкретный нативный BLOCK и возвращает `change_ref`. Preview не
записывает данные в SprutHub, но сохраняет локальную историю подготовленного
изменения с причиной.

`apply_automation_change` по `change_ref` повторно проверяет ссылки, типы,
доступность и права. Эквивалентный поддерживаемый BLOCK переиспользуется даже
при другом имени, только если его `active`, `onStart` и `sync` также совпадают.
Иначе инструмент возвращает `conflict` и не включает чужой сценарий и не создаёт
дубликат. Если сценарий нужен, создаётся ровно один объект, после чего его
конфигурация читается и сравнивается. Потеря или несовместимость ответа после
отправки create сначала приводит к сверке хаба; неизвестный исход остаётся
`uncertain`, а повторный apply не отправляет create вслепую.

`get_automation_change` сверяет локальную запись с хабом после перезапуска MCP.
`rollback_automation_change` удаляет только объект с маркером этого изменения и
точно ожидаемой конфигурацией. Добавляемый SprutHub после исполнения
`data.targets[0].state` считается runtime-состоянием блока `if`, а назначаемые
редактором `blockId` — производными идентификаторами структуры; прочие поля,
`delay.index`, настройки и действия остаются частью точной защиты. Ручная
правка даёт `conflict` и сохраняется. Удаление сценария не возвращает уже
изменившееся физическое
состояние лампы.

Перед удалением инструмент сохраняет локальное намерение отката и не отправляет
delete, если это не удалось. После наблюдения хаба исход, владение и результат
финального сохранения считаются отдельно для apply, status и rollback. Поэтому
отказ финального журнала не заменяет подтверждённые `applied`, `rolled_back`,
`already_present` или `conflict`: ответ добавляет `local_state.saved: false` с
безопасным действием восстановления. Неустановленный исход остаётся `uncertain`
и не утверждает, что сценарий не был создан. После восстановления каталога
следует вызвать `get_automation_change`; этот read-only инструмент вычисляет
актуальный статус, не переписывая журнал.
Однозначный отказ хаба остаётся `request_rejected`, даже если обратный переход
журнала в `prepared` сохранить не удалось. В таком случае старый `change_ref` не
повторяют: после восстановления каталога выполняют новый preview.

Локальная история привязана к URL и serial настроенного хаба через SHA-256 и не
содержит token. По умолчанию она хранится вне Git в системном каталоге состояния
пользователя; `SPRUT_AGENT_STATE_DIR` задаёт другой каталог, например для
изолированного запуска. Preview не является атомарной резервацией между ним и
apply. Пустой прямой список сценариев не доказывает отсутствие зависимостей
внутри произвольного кода или bridge-модуля. Поддерживается один пишущий
MCP-процесс на хаб: внутри него apply и rollback выполняются последовательно.
Межпроцессной блокировки нет. В наблюдённом API нет conditional delete, поэтому
инструмент блокирует откат при уже прочитанной ручной правке, но UI или другой
процесс всё ещё может изменить сценарий после последней проверки и до удаления.

из Git. Сырые записи могут содержать секреты; санитайзер пока не реализован.

**Границы совместимости.** Снимок `1.5.58` относится к сборке 2025-09-16.

на распознавании build. Отдельная функция извлечения protobuf-модулей успешно
прочитала текущий JS; нативные каталоги типов проверены на хабе.
[Источники и карта модели](research/protocol/2026-09-09-model.md) различают эти
проверки. Номер версии интерфейса сам по себе не подтверждает контракт хаба.

Нативные `room.list`, `room.get` и `accessory.list` с фильтром комнаты наблюдались
на Sprut.hub 2 с прошивкой `3.0.0b (20131)`. Источник и ограничения проверки —
в [записи от 2026-09-09](research/protocol/2026-09-09.md).

## Разработка

Нужны Node.js 24+, npm, Git и Codex CLI 0.154.0 или новее:

```sh
git clone https://github.com/xor777/sprut-agent.git
cd sprut-agent
npm ci
npm run check
```

Корневой `.mcp.json` запускает собранный сервер из checkout, если рабочий каталог
процесса — корень репозитория. Эквивалентная проверенная команда:

```sh
cd /absolute/path/to/sprut-agent
node ./dist/plugin/dist/server.mjs
```

Если MCP-клиент запускает процесс из другой папки, передай в `args` абсолютный
путь сервера: `/absolute/path/to/sprut-agent/dist/plugin/dist/server.mjs`.
Такой запуск не требует поддержки `cwd` клиентом. Установленный Codex plugin
использует собственную конфигурацию и `./dist/server.mjs` внутри своего
каталога, поэтому не зависит от checkout или текущей папки клиента.

Продуктовые ожидания проверяем через публичные точки входа. Тесты recorder
запускают отдельный процесс и локальный CDP-сервер; тесты MCP —
настоящий MCP-процесс и внешний тестовый WebSocket-хаб. Подмена внешнего хаба
не заменяет живую приёмку SprutHub.

```sh
npm run check           # Обязательные проверки: Biome и офлайн-тесты
npm run test:mutations  # Необязательная диагностика настроенной области
```

`npm run check` также воспроизводимо собирает минимальный поставляемый комплект,
проверяет отсутствие расхождения с Git и устанавливает plugin настоящим Codex
CLI в изолированный профиль. Тест проверяет effective transport через
`codex mcp get`, сохраняет прежний `sprut`, читает температуру через выбранную
установленную копию и запускает второй MCP-процесс с сохранённой сессией.
Отдельный контраст сохраняет занятую чужую запись `sprut-agent`, сообщает
исправимый конфликт и доказывает работу после явного удаления этой записи.
Живой SprutHub при этом не используется.

Попробовать сравнение на включённом в репозиторий снимке:

```sh
npm run research:diff -- \
  --from research/snapshots/1.5.58 \
  --to research/snapshots/1.5.58
```

Это сравнение снимка с самим собой: ожидается `Verdict: unchanged`.
Для содержательного сравнения передай два разных каталога снимков.

Переносимый agent-smoke устанавливает копию skill в новый временный профиль,
запускает публичный MCP на синтетическом хабе и сохраняет доказательства вне
репозитория:

```sh
npm run eval:spruthub-master
```

Команда требует локально аутентифицированный Codex CLI. Она подключает
существующий `auth.json` к временному профилю символьной ссылкой, не копирует его
в репозиторий или результат и не обращается к живому дому. Режим `plugin`
дополнительно начинает без компонентов продукта, устанавливает весь комплект
штатным CLI из текущей копии и только затем запускает новый диалог:

```sh
npm run eval:spruthub-master -- contact-option plugin
```

Ручной сценарий неоднозначного выбора запускает новый диалог Codex с
синтетическим внешним хабом и печатает трассу инструментов и ответ:

```sh
node research/check-agent-room-ambiguity.mjs ambiguous
```

Доступны также режимы `office` и `ambiguous-distinct`. Сценарий требует Codex CLI
и сетевого доступа к модели, не входит в `npm test`; exit code подтверждает только
завершение запуска. Соответствие ответа критерию оценивается по напечатанному
ответу вручную.

Обычный CI выполняет быстрые проверки и commitlint. Качество принимаем по
продуктовым тестам, независимому ревью и живой проверке на хабе. Адресные мутации
помогают разобрать конкретное сомнение в тесте. Полный Stryker запускается только
как отдельная диагностика, локально или вручную в GitHub Actions; обязательного
порога mutation score нет. Область задана в [конфигурации](stryker.config.json),
результат относится только к ней. Правила выбора проверки — в [AGENTS.md](AGENTS.md).

`npm test` проверяет MCP-путь через официальный клиент, настоящий дочерний
stdio-процесс приложения и внешний локальный WebSocket-сервер. Сценарии
покрывают полный каталог и выбор по ссылке, значения, единицы, контекст сервиса,
повторное чтение, неполные ответы, авторизацию, общий deadline вызова, обрыв и
восстановление. Температуры и мультисенсор проверяются по обезличенным
проекциям наблюдённых ответов хаба. Это офлайн-доказательство контракта,
а не живая семантическая проверка агента или гарантия совместимости
со всеми версиями SprutHub.

Используем Conventional Commits и отдельные RED/GREEN-коммиты для изменений
поведения. Git hooks проверяют сообщение коммита и запускают `npm run check`
перед push. Полные правила, включая владение рабочей копией и её уборку, —
в [AGENTS.md](AGENTS.md); [CLAUDE.md](CLAUDE.md) ссылается на тот же файл.
