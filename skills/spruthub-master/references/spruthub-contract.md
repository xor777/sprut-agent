# Проверенный контракт SprutHub

Прочитай нужный раздел, когда решение зависит от адресации, семантики native данных, доступного инструмента или версии. Это не полный API: актуальные поля и операции возвращают сами публичные инструменты.

## Дома и сущности

Наблюдение: Sprut.hub 2, firmware `3.0.0b (20131)`, 2026-09-09. Источник,
историческая привязка runtime и границы доказательства сохранены в
[журнале модели](https://github.com/xor777/sprut-agent/blob/main/research/protocol/2026-09-09-model.md).

- `list_homes` возвращает доступные дома. Все дальнейшие refs содержат percent-encoded serial выбранного дома; локальные ID разных домов нельзя смешивать.
- `inspect_home(home_ref)` даёт компактный каталог комнат, сценариев и extensions и честную `coverage`. Успешный list не доказывает, что соответствующий get также сработал.
- `get_entity(entity_ref, include, pointer?, max_bytes?, offset?, version?)` читает room, accessory, service, characteristic, scenario, extension, назначенную logic или окно физических настроек. Room даёт компактную иерархию физических accessory и вложенных service с их собственными ref/name/type без чтения значений; выбранный service затем раскрывается отдельно. `include` относится к указанной сущности и не является рекурсивным обходом её детей. `representation.kind=complete_entity` содержит полный `entity`; ограниченные `entity_overview` и `selected_value` вместо урезанного entity содержат отдельную `identity`. Карта `available_parts` показывает безопасные собственные key/name/type/ref/kind дочерних объектов и готовые адресные вызовы. RFC 6901 `pointer` применяется к уже нормализованной и redacted entity; сериализуемо отсутствующее значение не считается найденным. Версионное продолжение карты проверяет порядок указателей и identities. Для элемента с уникальным непустым `ref` или `key` оно не меняется из-за нового текущего значения; при отсутствующей или повторяющейся устойчивой identity версия консервативно учитывает весь нормализованный и уже скрытый элемент и может потребовать restart чаще. Большая строка читается точными Unicode-частями; продолжение без версии отклоняется, а изменение даёт `stale_entity_content` и вызов с начала. Завершение последней строковой части, `selected_complete` и `entity_complete` — разные факты.
- `read_services(home_ref, room_ref?, service_types?, max_bytes?, cursor?)` даёт ограниченную по фактическому UTF-8 размеру страницу native services с читаемыми текущими значениями. Каждый service сохраняет room и физический accessory; отсутствующая room metadata отмечается явно, а не удаляет service из результата. `service_types` сопоставляет точные native имена по OR, а `observed_service_types` показывает реально встреченные типы всей области, включая первую ограниченную страницу home. `false`, ноль, известный `null` и отсутствующее native значение различает `value_status`; enum и unit не выводятся из бытового названия. `scope_status` отделяет пустую область от `match_status: no_matches`. Продолжение привязано к последнему выданному service ref; исчезнувший ref даёт `stale_cursor` и следующий вызов для начала заново. Отдельные значения не обрезаются; слишком крупный service явно оставляет точный `get_entity` next вместо подмены данных. Каждая страница читается заново и не является атомарным снимком дома.
- У настройки есть конкретный владелец. `include=options` раскрывает native options для characteristic или назначенной logic ref. Безопасная характеристика возвращает `option_scope`: native `true`/`false`/`null`, статус `not_read`/`found`/`checked_empty` и точный следующий вызов. Для `characteristic.getOptions` прочитанную область подтверждает явный массив. Для `logic.getOptions` также наблюдён существующий пустой operation container: он означает известный пустой список; отсутствующий container, `null` или не-массивное значение остаются `incompatible_response`. Container include не запускает рекурсивное чтение: `include_resolution.not_applied` возвращает причину и безопасный следующий вызов, когда его можно построить по возвращённой ссылке, иначе явное ограничение. Terminal redacted marker не раскрывает refs, availability или include metadata.
- Physical window и назначенная logic — отдельные области: читай возвращённый window ref или logic ref самостоятельно. Пустой `physical_configuration.options` не означает, что у характеристики нет options; пустой результат характеристики не говорит о window или logic. В выводе различай «найдено», «эта область проверена и пуста» и «область не исследована».
- Запрашивай только нужные `options`, `relations`, `physical_configuration`, `diagnostics`. Каждый requested include для принятой сущности перечисляется как `applied` или `not_applied`; успешный ответ без такого исхода не считается полным обследованием устройства.
- `list_rooms` возвращает исходные имена и home-qualified room refs для `read_services` и `get_entity`; одинаковые значения разных комнат не объединяются.
- Native identity характеристики задают дом и `aId/sId/cId`; identity extension instance — непустой `extensionKey`, не общий `type`.

Официальное описание модели: [SprutHub Wiki, аксессуары, сервисы и характеристики, oldid 3538](https://wiki.spruthub.ru/index.php?title=%D0%90%D0%BA%D1%81%D0%B5%D1%81%D1%81%D1%83%D0%B0%D1%80%D1%8B,_%D1%81%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D1%8B_%D0%B8_%D1%85%D0%B0%D1%80%D0%B0%D0%BA%D1%82%D0%B5%D1%80%D0%B8%D1%81%D1%82%D0%B8%D0%BA%D0%B8&oldid=3538). Это модель/UI, не транспортная спецификация.

## Автоматизации и зависимости

### Модель исполнения и адресное чтение

Проверяй не упоминание устройства в каталоге, а цепочку исполнения: **определение → конкретное назначение или вызывающий код → его `active`, параметры и состояние → условие → команда target → состояние target → физический результат**. Это разные факты. Полный source подтверждает лишь определение; ACK команды, прочитанное значение и физический эффект также не выводятся друг из друга.

- **BLOCK** — сценарий с native `type=BLOCK`; его конфигурация содержит инициирующие `trigger`, условия, ветки действий и targets. Читай выбранный scenario ref через `get_entity` с `include=["configuration"]` и выполняй его `next` до нужного узла. Подтверждённые `scenario_roles` дают направление и `scenario_active`, но code-условие или code-action остаётся opaque и не доказывает ни прохождение условия, ни вычисляемую цель.
- **LOGIC** — переиспользуемое определение кода для назначаемого native type. Определение сценария, назначаемый type и назначение этого type на конкретном service — разные сущности: `scenario.index`, имя и scenario `type=LOGIC` не задают назначаемый type. `get_entity(service_ref)` отдельно возвращает `assigned_logics` и `available_logic_types`; наличие доступного типа не означает назначения. Для выбранного назначенного logic ref вызови `get_entity(..., include=["options"])` и проверь `active` и фактические options. Source определения сам по себе не показывает все сервисы с назначением, переданные состоянием параметры или динамически выбранный target.
- **GLOBAL** — вызываемый другими сценариями код с параметрами, а не назначение на service. Его эффект определяется вызывающим кодом, переданными данными и состоянием; `GlobalVariables` могут связывать разные сценарии. Публичного `get_entity` для значений `GlobalVariables` нет. Читай только выбранные определения и вызывающие code-фрагменты по точным scenario refs и `configuration` pointers. Если вызывающий узел, параметры или текущее значение недоступны, эта связь остаётся открытой даже после полного чтения GLOBAL source.

Адресный маршрут начинается с `get_entity` для target characteristic или accessory с `include=["relations"]`. Опирайся на доказанные `scenario_roles`, `assigned_logics` и межсущностные links; `scenario_associations` — только недирекционный кандидат. `scopes` задают исход и свежесть каждого native-чтения, а `unresolved_areas` сохраняют непрочитанный code/extension, неподдержанный BLOCK-узел и отсутствие runtime-наблюдения. Выполняй `next` только для роли или открытой связи, которая меняет бытовое решение. Для accessory дочерние характеристики не обходятся рекурсивно: используй возвращённые безопасные candidates. `checked_empty` доказывает отсутствие только в названной прочитанной области; локальное отсутствие назначения на target не исключает команду из logic другого service или вызывающего сценария.

Положительный и отрицательный вывод допустимы в действительно прочитанной области. Если связь definition → native type, назначение, параметры, вызывающий код или вычисляемый target не установлена, назови именно её вместе с уже доказанным поведением. Полная инвентаризация дома и длительное наблюдение нужны только когда могут изменить решение. Для проверки фактического исполнения используй ограниченное наблюдение ниже; оно не превращает отсутствие события в доказательство отсутствия физического сигнала.

Наблюдённый `link.list` с SYSTEM-связью контроллера не доказывает связь двух устройств. `characteristic.getOptions` может вернуть, например, `SwitchOffTime`; публичный `get_entity` раскрывает его через `include=options`, но это настройка собственного состояния датчика, а не правило другой лампы.

`get_scenario_sdk` читает текущий native `scenario.sdk` выбранного хаба по явному запросу. Поля `sdk`, `sdk_complete`, `bytes`, `sha256` и freshness относятся к этому ответу: `sdk_complete=true` подтверждает полный возвращённый текст; при скрытии credential `sdk_complete=false`, а `bytes` и `sha256` описывают возвращённый redacted marker, не недоступный исходник. Это протокольный источник API исполняемого на хабе кода, а не карта текущих вызовов и назначений; старый snapshot/frontend schema остаётся кандидатом до проверки.

Тип сценария устанавливается по native полям, не по имени. На целевом хабе наблюдались BLOCK/GLOBAL/LOGIC; другие имена из proto enum не доказывают доступный механизм создания. Официальная Wiki описывает LOGIC как код, назначаемый поддерживаемым типам service, GLOBAL как вызываемый код с параметрами, а BLOCK как конфигурацию, которая тоже может содержать code. Это общая модель, не доказательство конкретного назначения дома: [логические сценарии, oldid 3126](https://wiki.spruthub.ru/index.php?title=%D0%9B%D0%BE%D0%B3%D0%B8%D1%87%D0%B5%D1%81%D0%BA%D0%B8%D0%B5_%D1%81%D1%86%D0%B5%D0%BD%D0%B0%D1%80%D0%B8%D0%B8&oldid=3126), [основные элементы, oldid 2988](https://wiki.spruthub.ru/index.php?title=%D0%A1%D1%86%D0%B5%D0%BD%D0%B0%D1%80%D0%B8%D0%B8_%D0%B2_Sprut.hub_-_%D0%BE%D1%81%D0%BD%D0%BE%D0%B2%D0%BD%D1%8B%D0%B5_%D1%8D%D0%BB%D0%B5%D0%BC%D0%B5%D0%BD%D1%82%D1%8B_%D1%83%D0%BF%D1%80%D0%B0%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D1%8F&oldid=2988), [переменные, oldid 2041](https://wiki.spruthub.ru/index.php?title=%D0%92%D0%B8%D0%B4%D1%8B_%D0%BF%D0%B5%D1%80%D0%B5%D0%BC%D0%B5%D0%BD%D0%BD%D1%8B%D1%85_%D0%B2_%D1%81%D1%86%D0%B5%D0%BD%D0%B0%D1%80%D0%B8%D1%8F%D1%85_%D0%B2_%D0%B2%D0%B8%D0%B4%D0%B5_%D0%BA%D0%BE%D0%B4%D0%B0&oldid=2041).
- В BLOCK активный `trigger` задаёт источник запускающей проверки; остальные источники могут быть условиями без самостоятельного запуска. Это подтверждает [SprutHub Wiki о триггерах, oldid 738](https://wiki.spruthub.ru/index.php?title=%D0%A2%D1%80%D0%B8%D0%B3%D0%B3%D0%B5%D1%80%D1%8B_%D0%B2_%D1%81%D1%86%D0%B5%D0%BD%D0%B0%D1%80%D0%B8%D1%8F%D1%85_(%D0%B6%D0%B5%D0%BB%D1%82%D1%8B%D0%B5_%D0%BA%D1%80%D1%83%D0%B6%D0%BE%D1%87%D0%BA%D0%B8)&oldid=738). При уже запущенной проверке `EVERY` выполняет ветку Тогда или Иначе каждый раз, а `ONCE` — только при изменении результата условия; [Wiki основных элементов, oldid 2988](https://wiki.spruthub.ru/index.php?title=%D0%A1%D1%86%D0%B5%D0%BD%D0%B0%D1%80%D0%B8%D0%B8_%D0%B2_Sprut.hub_-_%D0%BE%D1%81%D0%BD%D0%BE%D0%B2%D0%BD%D1%8B%D0%B5_%D1%8D%D0%BB%D0%B5%D0%BC%D0%B5%D0%BD%D1%82%D1%8B_%D1%83%D0%BF%D1%80%D0%B0%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D1%8F&oldid=2988#%D0%A7%D1%82%D0%BE_%D0%B4%D0%B5%D0%BB%D0%B0%D0%B5%D1%82_%D0%B7%D0%BD%D0%B0%D1%87%D0%BE%D0%BA_%D0%B1%D0%B5%D1%81%D0%BA%D0%BE%D0%BD%D0%B5%D1%87%D0%BD%D0%BE%D1%81%D1%82%D0%B8_%D0%B2_%D1%81%D1%86%D0%B5%D0%BD%D0%B0%D1%80%D0%B8%D1%8F%D1%85) приводит примеры повторных показаний и неизменного результата. Официальный [frontend asset](https://beta.spruthub.ru/js/app.16735171810a795a9f2d.js), SHA-256 `81c1ef74ce21eb5ccff583255ba82fe766ff4cf6bc251c0566b7bd67436647f8`, связывает кнопку Infinity с native `EVERY`/`ONCE` и формулирует EVERY как выполнение веток «при каждой проверке условия». Режим ветки не гарантирует доставку обновления или сам запуск проверки.
- Native delay `RESET` начинает полный срок при каждом повторном входе в соответствующий delay-блок. Для входа хаб должен получить обновление, запустить проверку и выбрать содержащую delay ветку; событие с `condition=false`, при котором delay не посещён, таймер не перезапускает. Поэтому сохранённое `MotionDetected=true` не доказывает новый trigger. Доставка показания, проверка и выбор ветки, физическое движение, физическое окно датчика и timeout MCP-клиента — разные события и механизмы. Источник семантики delay — [SprutHub Wiki, oldid 1333](https://wiki.spruthub.ru/index.php?title=%D0%97%D0%B0%D0%B4%D0%B5%D1%80%D0%B6%D0%BA%D0%B0_%D0%B2%D1%8B%D0%BF%D0%BE%D0%BB%D0%BD%D0%B5%D0%BD%D0%B8%D1%8F&oldid=1333).
- `start_native_observation` использует отдельное соединение выбранного дома и сразу возвращает `observation_ref`; обычные чтения остаются доступны. По умолчанию окно длится 180 секунд и хранит до 200 событий, максимумы — 300 секунд и 500 событий. Один MCP-процесс ведёт одно наблюдение и хранит результат до следующего успешного старта или завершения процесса; `connection_lost`, `truncated` и `canceled` обозначают неполное окно.
- Наблюдатель объединяет выбранные characteristic/scenario events с `log.subscribe` сообщениями исполнения только точного выбранного индекса. Для проверенных native форм/path он сохраняет исходный текст, level/path, log time отдельно от локального получения и не выводит причинность из строки; соседние сценарии и общий account/API log отбрасываются. Поток сохраняет повторы, фактически дошедшие до WebSocket, но не является полным журналом физических или радиоотчётов. На проверенном command path повторная подтверждённая команда с тем же значением не породила второе characteristic event и новую проверку BLOCK; это не устанавливает поведение radio path датчика. [Обезличенное наблюдение границы command/event](https://github.com/xor777/sprut-agent/blob/main/research/protocol/2026-09-11-native-event-boundary.md).

Проверенное обезличенное наблюдение за хабом: [sprut-agent, automation context at 5d1372d](https://github.com/xor777/sprut-agent/blob/5d1372d40c4a8eb3b3a5c73f09303f9c0e885e50/research/protocol/2026-09-09-automations.md).

## Значения, свежесть и диагностика

- `freshness.hubResponseReceivedAt` — время получения ответа. `measurementAt: null` или `source_timestamp: null` означает, что время источника неизвестно.
- Configured value, диагностический report и `pending: unknown` не выводятся друг из друга.
- GROUP layout, BUTTON command и NUMBER setting — разные классы данных. Нельзя объявлять команду текущей конфигурацией.
- Диагностика и код раскрываются только по явному include. Sensitive native entity возвращается терминальным redacted marker; не пытайся восстановить скрытых потомков или identifiers.

## Поддержанная запись

Общий публичный write-path сначала раскрывает версионный контракт через
`get_native_change_contract`, затем разделяет `prepare_native_change`,
`apply_native_change`, `get_native_change` и `restore_native_change`.
Статические контракты `room_create` и `virtual_light_group` читаются по одной
`operation` без угадывания цели. Явно переданный `target_ref` для них должен быть
точной ссылкой настроенного дома; прочие зависимые от сущности контракты требуют
подходящую home-qualified ссылку. Это чтение описывает возможность механизма, но
не проверяет выбранные комнаты, лампы или готовность конкретного изменения.
`list_native_changes` даёт небольшую страницу истории по дому и точной entity ref,
включая старые automation changes. Возвращённый `next` сохраняет дом, фильтр и
размер страницы; его выполняют до явного `null`. Cursor другой области отклоняется,
а сохранённая граница порядка продолжает работать, если ограничивающую запись
прочитали, переместили или удалили. Страницы читают текущий порядок журнала, а не
атомарный снимок: новое или обновившееся изменение перед cursor не появляется в
его продолжении. `recorded_status` —
сохранённый исход на `updated_at`, а не текущая проверка; для неё используется
адресный `next` самой записи. У `block_action_pause` отдельный `effect_status` вычисляется из
сохранённого абсолютного срока и не выдаёт `applied` за ещё активное исключение.
Для BLOCK история индексирует canonical refs
сценария и участвующих accessory/service/characteristic до и после update;
старые unqualified refs привязываются только к fingerprint текущего журнала.
Это поиск, а не разрешение на запись.

Локальная история привязана к URL и serial хаба через SHA-256 и не содержит
token. По умолчанию она хранится вне Git; `SPRUT_AGENT_STATE_DIR` задаёт
изолированный каталог. Один MCP-процесс сериализует apply/restore, но
межпроцессной блокировки нет. Preview не резервирует состояние до apply, а в
наблюдённом API нет compare-and-set или conditional delete.

- `accessory_placement` принимает точные home-qualified refs одного accessory и
  существующей комнаты, сохраняет исходные имя, комнату и физическую привязку,
  затем отправляет только `accessory.update({id,name,roomId})`. Пустой ACK
  подтверждается отдельным `accessory.get`; requested и observed имя различаются,
  если хаб нормализовал строку. Restore возвращает только имя и комнату при
  совпадении всего применённого снимка и привязки. Соседние accessories с тем же
  `deviceId`, services и сценарии не меняются.
- Подготовка `room_create` требует home ref и отсутствующее точное имя. Подтверждённый
  `RoomMessage` сохраняет ID созданной комнаты; повтор после рестарта читает её,
  а не создаёт дубликат. После потерянного ответа новые одноимённые комнаты
  возвращаются как кандидаты без владения, и create не повторяется вслепую.
  Если свежий каталог не находит комнату, старый change остаётся uncertain;
  новый `room_create` повторно проверяет отсутствие до записи.
  Restore удаляет только подтверждённо собственную, неизменённую и пустую
  комнату. Сначала нужно восстановить размещённый в ней accessory. Контракты
  create/delete подтверждены официальными frontend/protobuf, но не live-опытом.
- `virtual_light_group` требует не менее двух `Lightbulb` service с общими
  `On` и `Brightness`, создаёт один виртуальный `Lightbulb` и связывает ровно
  эти две явно выбранные характеристики в режиме `LastValue`. Этот режим
  сохраняет
  индивидуальное управление участниками, но после их ручного расхождения повтор
  уже отображаемого виртуального значения может получить ACK без доставки всем.
  При apply `characteristic_value` к успешно применённой собственной группе,
  известной текущему журналу, инструмент читает каждого участника и возвращает
  `uncertain/group_members_not_converged`, если они не сошлись. Для существующей
  или чужой группы `characteristic_value` подтверждает только виртуальный scalar;
  состояние участников агент читает независимо. Restore удаляет только
  принадлежащие change links и
  неизменённый виртуальный accessory, не переписывая физические участники.
- `characteristic_value` проверяет фактический native type, права, kind,
  диапазон, шаг, длину и перечисление. Для подтверждённых постоянных настроек
  `TargetTemperature`, `TargetHeatingCoolingState` и `C_FanSpeed` контракт и
  подготовленный change заранее показывают `restore_supported=true`, только если
  сохранённый baseline сам проходит тот же native validator. Иначе чтение и
  подготовка сохраняются, но `restore_supported=false` и
  `restore_limitation=baseline_not_writable` честно показывают границу до apply.
  Уже выбранное значение считается no-op только для этих известных настроек;
  равная сохранённому значению команда неизвестной семантики остаётся явным
  подготовленным действием и может повторно синхронизировать исполнитель.
  Restore возвращает сохранённое значение только после доказанного apply и
  только пока текущее значение совпадает с применённым; ручная настройка не
  перезаписывается. Наблюдённая ручная настройка навсегда снимает у конкретного
  change право присвоить или вернуть значение; публичное поле
  `manual_change_observed=true` сохраняет этот факт после restart. Последующее
  совпадение с requested остаётся `conflict/manual_change`, в том числе если то
  же значение применил другой change. Для поддержанного возврата совпадение с
  baseline завершает restore без записи; неподдерживаемая команда или baseline
  остаются `conflict/manual_change` с наблюдением baseline, а не становятся
  `restored`. Для следующей разрешённой записи агент читает текущее значение и
  создаёт новый change. Третье значение после неизвестного исхода apply или
  restore становится `conflict/manual_change`; повтор и restart сохраняют этот
  ручной выбор и `write_intent.phase=needs_reconciliation`, не выдавая
  неизвестную прошлую отправку за неприменённое изменение. Журнал опубликованной
  версии с `conflict_reason=manual_change` сохраняет ту же границу владения,
  даже если старый `write_intent.phase` уже равен `reconciled`. Опубликованный
  журнал, где прежний restore заменил такой conflict на `not_owned`, также не
  получает право новой записи: сохранённое третье значение восстанавливает
  `manual_change_observed`, а `native_write_sent=true` не превращается в
  `change_was_not_applied`. Для нового действия агент создаёт новый change.
  Это возврат выбранной настройки, а не отмена уже
  случившегося нагрева, охлаждения или вентиляции, поэтому
  `physical_effect_reversible=false`. Остальные characteristic types считаются
  командами или неизвестной семантикой и не получают restore только из-за
  read/write scalar-контракта. Readback остаётся наблюдением значения, а не
  доказательством физической причинности. После неизвестного исхода apply или
  restore characteristic-команда и климатическая настройка автоматически не
  отправляются повторно; для следующей разрешённой записи после утраты владения
  нужен новый подготовленный change.
- `characteristic_option`, `logic_option` и `window_option` принимают точный ref
  владельца и один option key. Общий контракт допускает только
  readable/writable/enabled `NUMBER` с `intValue`/`longValue`/`doubleValue`,
  `CHECKBOX` с `boolValue` или `LIST` с непустыми scalar `validValues` того же
  kind. Известный `GenericBoolean`/`GenericInteger`/`GenericLong`/`GenericDouble`
  обязан совпадать с envelope. Явные min/max/step и список сохраняются и
  проверяются; LIST, в котором хотя бы один вариант противоречит явному
  диапазону или шагу, целиком несовместим. Отсутствующие ограничения не
  выводятся из имени. GROUP, кнопки, PASSWORD, чувствительные option,
  произвольный текст и составные значения не записываются; чувствительная
  настройка блокируется до сохранения baseline или истории. В ответе
  чтения `native_change` отдельно показывает native write, поддержку публичной
  операции, причину отказа и точный `get_native_change_contract` next.
  Текущее значение находится в `option.value`, а не в
  `validValues[].checked`. Уже нужное значение не создаёт change. Запись
  отправляет только выбранные key и typed value; readback выполняется отдельным
  `characteristic.getOptions`, `logic.getOptions` или `window.get`.
  Restore возвращает сохранённый baseline только при совпадении текущего
  значения с доказанно применённым; подготовленный или подтверждённо
  отклонённый change не присваивает совпавшую ручную настройку и возвращает
  `not_owned`. Обычный неизвестный option-write или изменение `logic_active`
  можно повторить после readback неизменённого baseline, пока журнал не
  зафиксировал утрату владения. Уже отправленный `not_owned` требует нового
  prepare и повторно не записывается.
  Третье значение не затирается; conflict возвращает имена
  исходного, применённого и текущего вариантов и эффект нового изменения,
  которое можно подготовить только после решения владельца.
- `logic_assignment` применяет различие definition, type и назначения из
  «Модели исполнения и адресного чтения»: принимает logic ref из
  `available_logic_types` выбранного
  service. Существующее назначение даёт no-op без владения; отсутствующий тип
  даёт `logic_type_unavailable`. Новое назначение создаётся неактивным, а потеря
  ответа сверяется по scoped service/type без второго create. Снимок созданной
  logic включает options; удаление допустимо последним только после возврата
  `active` и типизированных значений options к этому снимку. Изменение подписей,
  локали и флагов представления не меняет конфигурацию. Пока `active`, состав,
  тип или значение options отличается, назначение остаётся принадлежащим change,
  но удаление блокируется с указанием отличающихся ключей без догадки об авторе.
  После достоверно наблюдённого исчезновения созданного назначения change
  сохраняет утрату владения: повторное появление того же service/type не
  присваивается ему и не удаляется. Неудачное чтение само по себе владение не
  снимает и не выдаёт сохранённые различия за текущие.
  Настраиваемое назначение выполняй безопасной последовательностью: назначь
  неактивным, прочитай фактические options через `include=options`, настрой их
  отдельными `logic_option` changes и активируй через `logic_active` последней.
  Возвращай в обратном порядке: деактивируй, восстанови options и только затем
  удали созданное назначение.
  Исчезновение и пересоздание между успешными чтениями неразличимы; сохранение
  утраты владения между процессами требует успешной записи журнала.
- `logic_active` использует boolean value-change. Значения option не зашиты по
  имени владельца, модели или ключу. Все три option-операции используют
  общий журнал направления apply/restore, отдельный readback и защиту ручной
  правки; уже нужное значение не создаёт change.
  Options сохраняются по service/type после удаления и пересоздания назначения.
  Отмена `logic_option` возвращает наше неизменённое значение по этому адресу
  даже после пересоздания; это не даёт права удалить новое назначение.
- `logic_source_create` принимает точный service ref, полный source и явные
  `name`, `description`, `active`, `on_start`, `sync`. Он создаёт native
  `type=LOGIC`, добавляет к отправленному source уникальный JS-комментарий
  владения и читает результат обратно как точный текст. Подтверждённый source
  остаётся `applied` независимо от mapping: `logic_mapping_status` и
  `logic_assignment_ready` отдельно показывают возможность назначения.
  Если хаб вывел `description` из JS или нормализовал create flags, change
  отдельно показывает запрошенные и `observed` metadata с
  `exact_match:false`; сохранённый наблюдённый снимок остаётся границей защиты
  от последующей ручной правки.
  Для этой операции mapping definition → назначаемый type устанавливается
  только по единственному новому значению свежего `logic.types`.
  При `missing` source можно исправить через его `scenario_ref`. При
  `ambiguous` изменение source само по себе не выбирает один из одновременно
  появившихся типов; mapping перечитывается после устранения лишнего кандидата.
  Удалять source до подтверждённого mapping нельзя: неизвестный type может иметь
  назначение на другом сервисе. Собственный маркер в source позволяет найти
  именно результат потерянного create без второй отправки и без присвоения
  соседнего совпадающего сценария. В журнале сохраняется точный отправленный
  source, но наружу change возвращает его SHA-256 и результат точного сравнения,
  а не повторяет сохранённый код.
- `logic_source_update` поддержан только для непрерывно наблюдаемого
  пользовательского LOGIC и отправляет только `{index,data}`; отдельный readback
  проверяет точный source и сохраняет фактически наблюдённые metadata. Хаб
  заново выводит из JS `name` и `description`; остальные metadata инструмент
  берёт из фактического readback. Без CAS он не приписывает любое отличие source
  или параллельной правке. Полный снимок до apply
  и применённый снимок до restore остаются строгими guards ручной правки. После
  обратной записи readback подтверждает точный исходный source и снова сохраняет
  наблюдённые metadata. Predefined source доступен для чтения и клонирования, но
  не изменяется. Restore update не затирает ручную правку. Restore create перед delete сканирует текущие
  назначения подтверждённого native type по сервисам дома; omitted `services`
  трактуется как пустое repeated-поле, а present malformed ответ отклоняется.
  Любое назначение блокирует удаление. После снятия дочерних source/options/
  active changes и назначений созданный неизменённый LOGIC можно удалить.
  Source readback не подтверждает callback lifecycle или физический эффект; JS
  локально не исполняется и не проходит обещанный полный static analysis.
- На Sprut.hub `3.0.0b (20131)` для Lightbulb service подтверждён доступный тип
  `SmoothBrightnessChange`: после назначения его options `StartValue`,
  `EndValue` и `Duration` имеют `GenericInteger/NUMBER` и `intValue`, а
  `Duration` задаётся в секундах; `primary` является GROUP и не записывается.
  Эти имена помогают выбрать наблюдённый контракт, но runtime всё равно читает
  фактический каталог и options и не зашивает этот тип или ключи.
- `block_create` требует явные `name`, `description`, `active`, `onStart`,
  `sync`, `type=BLOCK` и `data`. После неопределённого create маркер позволяет
  сверить хаб без повторной отправки.
- `block_data_update` заменяет полное `data` и отправляет только `{index,data}`:
  изменение имени и runtime-флагов этим контрактом не поддержано. Ответ хаба
  может не содержать data, поэтому обязательна отдельная сверка.
- `block_action_pause` требует ref существующего BLOCK, RFC 6901 pointer на один
  узел исполняемой ветки (`if`, `service` или `delay`), положительную длительность
  в секундах и причину. Условие, set-поле, произвольное поле и отсутствующий путь
  отклоняются до записи. Полный baseline защищает смысл pointer до apply.
  При первом apply абсолютный срок сохраняется в том же intent до RPC; native
  узел `if/EVERY` с одним принадлежащим операции code-condition возвращает
  `Date.now() >= срок`, содержит исходное действие в `then` и пустой `else`.
  Срок исполняется хабом без клиента. Он открывает действие только для следующего
  обычного запуска и не проигрывает пропущенные события задним числом.
- Повтор apply одного change сохраняет исходный срок и не отправляет вторую
  обёртку. Подтверждённый `request_rejected` остаётся `not_applied`: до прежнего
  срока тот же change можно безопасно отправить повторно, после срока он уже не
  записывает истёкший контроллер. Новое поручение,
  выбравшее собственную обёртку или её непосредственное исходное действие
  `then/0`, заменяет одно окно без вложения. Старый change сразу становится
  `superseded`, остаётся таким после restore нового и виден этим в обычной
  истории без предварительного get.
- Идентичность собственной паузы задают change marker, точная форма/срок и
  канонические home/scenario IDs, не сохранённая позиция pointer. Поэтому сдвиг
  неизменённого контроллера соседней правкой не теряет владение. Неизвестный,
  изменённый или дублированный marker владения не даёт. Более узкий или широкий
  выбор, пересекающий уже отдельную паузу, отклоняется с текущими адресами, а не
  расширяется молча. Подграф, содержащий `trigger=true`, нельзя оборачивать до
  подтверждения регистрации вложенного trigger; самостоятельное действие без
  trigger этим не запрещено.
- Restore текущей паузы удаляет только найденный неизменённый управляющий
  контейнер, сохраняя актуальное действие из `then`; изменение code-condition,
  веток или формы контейнера даёт conflict. Разрешение этого собственного
  code-condition не разрешает иной JavaScript в BLOCK.
- После срока обёртка инертна. Следующий подготовленный `block_data_update` того
  же сценария схлопывает только точное собственное истёкшее условие в той же
  плановой записи и сохраняет актуальный дочерний узел. После подтверждённой
  уборки pause change имеет терминальный `completed`, `effect_status=expired`;
  его get/restore не сообщают конфликт и не записывают хаб. Read-only вызовы не
  чистят конфигурацию. Native source update может отменить уже запущенные delay
  прежней версии сценария; отдельного исполнения ровно в deadline нет. Статус
  `active`/`expired` MCP оценивает по своим часам, а условие — по часам хаба;
  синхронность часов не доказана.
- Restore обычного `block_data_update` сохраняет точные активные собственные
  контроллеры из baseline, но перед записью удаляет из него истёкшие,
  `completed`, `restored` и `superseded` обёртки. Явное удаление точного
  собственного активного контроллера обычной авторизованной правкой завершает
  паузу как `restored`; неизвестное исчезновение или изменённый срок владения не
  дают и остаются conflict.
- BLOCK manifest версии `2026-09-10` допускает `root.targets`, вложенные `if`
  (`EVERY`, нулевые branch delays), `AND`/`OR`, characteristic conditions с
  опубликованными comparisons, service/set и delay `RESET`. Нужен хотя бы один
  `trigger=true`; одна характеристика не может быть условием и действием.
- Все `aId/sId/cId` и native types проверяются в настроенном доме. Новый BLOCK
  не принимает неизвестные поля; update обязан сохранить их без изменений.
  Семантическая сверка игнорирует `blockId` и runtime `if.state` только на
  известных путях BLOCK; одноимённые поля vendor-поддерева не отбрасываются.
- В API нет compare-and-set. Проверка baseline снижает риск, но не закрывает
  гонку между последним чтением и записью. Перед apply и восстановлением data
  заново проверяются применимые права, bindings и значения. Restore BLOCK
  разрешён только при совпадении текущей конфигурации с применённым снимком;
  ручная правка даёт conflict и сохраняется. Завершённый `restored` терминален
  для change ref; повторное изменение требует нового prepare.
- Сохранённое намерение различает apply и restore, а ACK относится только к
  текущей попытке. `verification.fresh=false` означает отсутствие нового
  readback: прошлый outcome и последнее наблюдение могут быть показаны, но не
  считаются текущей проверкой.

Специализированная публичная запись boolean source → boolean target остаётся
совместимым путём:

1. `preview_boolean_automation` заново читает source/target и владельцев поведения, строит native BLOCK и возвращает `change_ref`. Он не меняет хаб, но сохраняет локальную историю.
2. `apply_automation_change` повторно сверяет refs и конфликты. Не воспроизводи алгоритм equivalence по памяти: используй фактический preview/status и его причину. Совместимый существующий BLOCK переиспользуется; близкий сценарий с несовместимыми runtime-флагами или семантикой даёт conflict, а не дубликат. В проверенном runtime `onStart` и `sync` должны быть выключены.
3. После отправки create неопределённый ответ сначала сверяется с хабом. Неизвестный исход остаётся `uncertain`.
4. `get_automation_change` перечитывает актуальный статус без изменения хаба.
5. `rollback_automation_change` удаляет только принадлежащий change объект с ожидаемой семантической конфигурацией. Ручная правка блокирует удаление; rollback сценария не возвращает физическое состояние устройства.

Для motion → light поддержан необязательный `auto_off_after_seconds`: он
добавляет `RESET` delay с выключением по семантике, описанной выше в разделе
«Автоматизации и зависимости». Это не доказательство времени последнего
физического движения. Источник — [SprutHub Wiki о задержке, oldid
1333](https://wiki.spruthub.ru/index.php?title=%D0%97%D0%B0%D0%B4%D0%B5%D1%80%D0%B6%D0%BA%D0%B0_%D0%B2%D1%8B%D0%BF%D0%BE%D0%BB%D0%BD%D0%B5%D0%BD%D0%B8%D1%8F&oldid=1333).

Options других владельцев и форм, pairing, backup, GLOBAL и иные виды
произвольного кода этим контрактом не поддерживаются. `window_option`
подтверждает настройку хаба, но не доставку до устройства и не физический
результат после отключения питания.
Первый login настраивается локальным credential-файлом и не является native
change. Не подменяй отсутствующие операции raw RPC или `write: true` в данных.
