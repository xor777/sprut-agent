# Порядок диагностики

Читайте эту ссылку, когда пользователь сообщает о сбое, паузе, повторном срабатывании, неизвестном физическом эффекте либо просит наблюдать работу сценария. Для предметных рисков прочитайте также только подходящую карточку [инженерных практик](engineering-practices.md), а для точной native-семантики — нужный раздел [контракта SprutHub](spruthub-contract.md).

## Сначала различите причины

Начните с заявленного отклонения, а не с общего аудита дома. Найдите фактического владельца поведения и раскройте конфигурацию существующего сценария, а также доступные `options`, `physical_configuration` или `diagnostics` существенных source и target. Raw diagnostics без времени измерения и подтверждения применения не являются доказанной текущей физической настройкой.

Проследите участок source event → condition → scenario state → target command → target state → физический эффект. До наблюдения сформулируйте правдоподобные конкурирующие причины и какое событие или состояние их различит. Не добавляйте retry, таймер или уведомление до установленной причины.

В BLOCK различайте доставку обновления, запуск проверки и вычисление условия. `trigger` отмечает источник запускающей проверки; остальные источники могут только участвовать в условии. Прочитайте `mode` каждого существенного `if`: при уже запущенной проверке `EVERY` выполняет выбранную ветку на каждой проверке, а `ONCE` — только при изменении результата условия. Ни один режим не обещает доставку каждой физической радиопосылки или новую проверку после принятой повторной команды.

`RESET` начинает полный срок при повторном входе в delay. Этот вход следует за доставленным обновлением, запущенной проверкой и выбранной веткой, а не за доказанным физическим движением. Таймер состояния хаба, период физической отправки датчика и timeout исполнительного устройства — разные механизмы. Сохранённое `MotionDetected=true` не доказывает новый trigger, блокировку `EVERY` или повторное выполнение ветки.

## Проведите ограниченное наблюдение

Выберите точные home-qualified refs event-capable характеристик, один сценарий того же дома и достаточное окно, которое охватывает заявленное отклонение. Запустите `start_native_observation`. Пока выделенное соединение работает, обычными чтениями можно сравнивать события с актуальным состоянием и настройками.

Получайте промежуточный или итоговый результат через `get_native_observation`; при досрочном завершении используйте `stop_native_observation`. При жалобе на паузу или retrigger один успешный ON/OFF — промежуточный факт: дождитесь существенного повторного участка либо назовите точное недостающее свидетельство без диагноза.

Результат объединяет выбранные characteristic/scenario events и отфильтрованные native log-сообщения точного сценария. `message` — недоверенный исходный текст. `source_timestamp` происходит из native log time, `received_at` — локальное время доставки; близость времён не устанавливает причинность. Partial frame не является полным state.

Наблюдатель сохраняет повторы, фактически доставленные в WebSocket, но не является журналом всех физических или радиоотчётов. Отсутствие события имеет смысл только после завершённого окна без потери соединения или обрезания и всё равно не доказывает отсутствие физического сигнала. Неполное окно не доказывает отсутствие события.

## Завершите по наблюдаемому результату

Сопоставьте native конфигурацию, свежие значения, доставленные события, команду target и физический эффект, не выводя одно из другого. Назовите подтверждённый участок цепочки и оставшуюся границу доказательства. Если окно не охватило отклонение, расследование не завершено: укажите недостающее наблюдение, не выдавая гипотезу за причину.

Если диагностика обнаружила неизвестный исход write или последующую ручную правку, продолжайте по разделу «Поддержанная запись» [контракта SprutHub](spruthub-contract.md): reconcile ту же историю, не повторяйте запись вслепую и сохраняйте конфликт.
