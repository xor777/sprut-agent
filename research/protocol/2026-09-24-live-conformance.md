# Живое соответствие: комната, BLOCK-формы по схеме, частичные записи, LOGIC

2026-09-24, 12:09–12:14 UTC. Цель: проверить на настоящем хабе формы и
операции, которые реализованы только по схеме редактора, и частичные
записи сценария. Все обращения шли через публичный MCP собранного комплекта.

## Источник и полномочия

- Хаб: firmware 3.0.0, revision 20131 (`list_homes`), model 2.
- sprut-agent 0.1.44, Git `1bd4c68`, `dist/plugin/dist/server.mjs` этого
  коммита. Скрипт `research/live-conformance.mjs`, MCP SDK client по stdio,
  журнал изменений во временном каталоге вне репозитория.
- Полномочия владельца: читать всё; создавать объекты и удалять все созданные
  в том же прогоне; не менять состояние дома; созданный BLOCK не должен иметь
  возможности сработать до удаления.
- Охрана в скрипте: запись только через prepare/apply/restore; создаются
  комнаты, BLOCK и LOGIC с префиксом `zz-sprut-agent-probe-20260924T121158Z`;
  менять и восстанавливать можно только созданные объекты; BLOCK создаётся с
  `active=false`, `onStart=false`; включить можно только BLOCK, чей
  единственный триггер — one-date cron 2030 года или позже.

Имена дома, serial, реквизиты и сырые ответы в Git не сохранены. Снимок дома
хранит имена только как SHA-256.

## Дефект 1: BLOCK с inc/dec нельзя удалить после создания

Контракт `block_create` публикует для `inc`/`dec` поле `value` как строку
(`native_scalar_as_string`). Отправлено в `scenario.create`, поле `data`:

```json
{"type":"inc","cId":16,"hc":"Brightness","value":"10"}
```

`scenario.get` после создания:

```json
{"type":"inc","blockId":25,"cId":16,"hc":"Brightness","value":10}
```

То же для `dec`. У `set` строковое `value` (`"false"`, `"true"`) хаб
сохранил как строку.

Продукт сравнивает data строго, поэтому сразу после собственного создания
`apply_native_change` вернул `conflict`, `conflict_reason: manual_change`,
`verification.result: requested_configuration_missing`,
`restore_supported: false`. `restore_native_change` ответил тем же `conflict`
и не удалил сценарий. Индекс созданного сценария (`scenario_index: "50"`)
известен из ACK, в `desc` стоит маркер владения этого изменения. Агент,
который выполняет опубликованный контракт, получает BLOCK, который он не может
отменить. Ошибку он видит как ручную правку владельца.

Остаток: `scenario/50`, `zz-sprut-agent-probe-20260924T121158Z-block-schema`,
`active=false`, `onStart=false`, `sync=false`. Он не может сработать.
Удалить его можно только вручную в интерфейсе SprutHub. По правилу владельца
прогон на этом остановлен, шаги 3 и 4 не выполнялись. Скрипт теперь создаёт
inc/dec только с `--include-orphaning`.

## Дефект 2: пустая комната не читается, созданную комнату нельзя удалить

`get_entity` и `read_services` с `room_ref` для существующей комнаты без
устройств (в каталоге дома у неё нет сервисов) вернули `incompatible_response`
«SprutHub returned an incompatible entity list.». Чтение комнаты разбирает
`accessory.list{roomId}` через `extractEntityArray` без
`missingMeansEmpty`. Вероятная причина: хаб опускает пустое повторяемое поле,
как наблюдалось для `extensionChild.list` 2026-09-17; сырой ответ не
записывался. Восстановление
`room_create` вызывает `listAccessoriesInRoom` с тем же разбором, а созданная
комната всегда пуста. Значит, `restore_native_change` не удалит созданную
комнату. Симулятор тестов всегда отдаёт `accessories: []` и дефект не
покрывает.

Доказано живым чтением и путём в коде. Само удаление на хабе не проверялось:
комната не создавалась, чтобы не оставить неудаляемый объект. Скрипт создаёт
комнату только после успешного чтения существующей пустой комнаты.

Уточнение того же дня (Architect, живое чтение того же хаба):
`accessory.list{roomId}` пустой комнаты отвечает объектом списка без поля
`accessories`, как `extensionChild.list` 17 сентября. Все поля списков в
[proto-схемах](2026-09-15-native-inventory/proto/) — proto3 `repeated`, так
что sprut-agent теперь читает объект списка без массива как пустой список для
всех native list; отсутствующий объект списка, `null` и не-массив остаются
`incompatible_response`. Удаление созданной комнаты после исправления на хабе
не проверялось.

## Итоговое состояние

Исходный и итоговый снимки дома отличаются одним добавленным сценарием
`scenario/50`. Чужие комнаты, сценарии (флаги и SHA-256 конфигураций),
аксессуары, сервисы и типы логик опорного сервиса не изменились. Контрольный
BLOCK удалён и проверен отсутствием. Проверка чужих комнат и сценариев после
шага 1 расхождений не нашла; после шага 2 прогон уже был остановлен.

## Ограничения

- Один хаб и одна версия прошивки. Проверено хранение и чтение, а не
  исполнение сценариев и не физический эффект.
- Не проверены: переименование и удаление комнаты, частичные записи
  `scenario.update{index,active}`, `window.update` Name/Desc и
  `scenario.update{index,data}` на владельце, жизненный цикл LOGIC.
  Для них нужен новый прогон с разрешения владельца после удаления
  `scenario/50`.
