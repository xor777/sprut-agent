# Удаление сценария: индексы, ссылки, назначения LOGIC, повторное создание

O20261023-scenario-delete, 2026-10-23. Цель — до удаления сценариев по
просьбе владельца (строка D25 [карты действий](2026-09-24-web-client-action-map.md),
`scenario.delete {index}`) установить на хабе, что удаление делает с
индексами остальных сценариев, ссылками из других BLOCK и назначениями
LOGIC, удаляются ли включённые сценарии и можно ли вернуть удалённый
сценарий из снимка.

## Полномочия и процедура

- Правило владельца: читать всё; создавать только свои временные объекты и
  сразу удалять; свои сценарии включать, только если они действуют на свои
  временные виртуальные устройства; сценарии владельца не удалять и не
  менять.
- Имена: сценарии — `zz-sprut-agent-probe-20261023T133418Z-<роль>`,
  комната и виртуальная лампа — `zz-probe-20261023T133418Z`. Охрана скрипта
  удаляла и меняла сценарий, только если индекс создан этим прогоном и
  `scenario.get` перед записью показывал имя с префиксом.
- Объекты: BLOCK без узлов (`{"targets":[]}`); BLOCK, чей единственный узел
  `if` срабатывает от one-date cron `0 0 12 1 1 ? 2030` и действует либо на
  свою виртуальную лампу (`On=false`), либо целями `scenario` (FIRE и
  DEACTIVATE) на свой BLOCK; LOGIC — объект `info` и пустой `trigger`;
  GLOBAL — одна строка комментария. Включались только такие LOGIC, GLOBAL и
  BLOCK с действием на свою лампу.
- Перед прогоном перечитаны мосты: у всех четырёх
  `AutoAddNewAccessory=false`, своя лампа никуда не экспортировалась.
- Скрипт репетировался на симуляторе (`apartment`). Первый живой запуск
  остановился до записей: чтение назначений по всему дому получило
  `-32603 Not found: 'Accessory 170'` на аксессуаре, который был в
  `accessory.list` (см. «Влияние на дом»). Второй запуск прошёл целиком.
- После каждой записи — пауза 0,8–1,0 с и чтение `scenario.get {expand:
  data}`, `scenario.list`, при LOGIC — `logic.list`, `logic.get`,
  `logic.types` своей лампы.

## Подтверждённые выводы

- `scenario.delete {index}` удаляет сценарий любого из проверенных типов
  (BLOCK, LOGIC, GLOBAL) во включённом и выключенном состоянии, без
  предварительного выключения и без отказа из-за ссылок или назначений.
  Индексы остальных сценариев не сдвигаются.
- В пределах прогона удалённый индекс больше не выдавался: счётчик хаба
  растёт и не заполняет пропуски, даже наибольший удалённый индекс. Но
  между 24.09 и 23.10 счётчик сбросился (68 и 69 выданы дважды), поэтому
  удалённый номер со временем может достаться новому, другому сценарию; когда
  именно сбрасывается счётчик (перезапуск, обновление прошивки), не
  установлено. Повторно созданный сценарий получает новый индекс, а
  `optionsWindow` у пользовательских сценариев равен индексу.
- Ссылки на удалённый сценарий из целей `scenario` других BLOCK хаб не
  трогает и не проверяет: они остаются висящими, и хаб сохраняет такие
  ссылки при записи и создании. После повторного создания они указывают на
  старый, несуществующий индекс, а после сброса счётчика могут указать на
  чужой новый сценарий с тем же номером.
- Назначения удалённого LOGIC хаб удаляет вместе с ним; повторное создание
  LOGIC их не возвращает. Назначение пришлось бы создать заново на новый тип
  (= новый индекс); его `active` и опции назначения при этом не сохраняются
  сами.
- Сценарий восстанавливается одним `scenario.create` из снимка
  `scenario.get {expand: data}`: `type, name, desc, active, onStart, sync,
  data`. Для BLOCK и GLOBAL это все хранимые поля; у LOGIC имя, описание и
  `onStart` всё равно берутся из `info` кода
  ([волна 4](2026-10-13-wave4-contracts.md), 1.5, 1.6), поэтому и они
  совпадают.
- Значит, «верни как было» для удаления может честно обещать только: тот же
  сценарий с тем же содержимым и флагами, но под новым номером; ссылки из
  других BLOCK и назначения LOGIC не возвращаются, если их не переписать или
  не создать заново отдельно. Сверка «тот ли это сценарий» по одному индексу
  после удаления недостаточна: номер может быть выдан заново.

## Расхождения симулятора с хабом

- Совпало: удаление не сдвигает индексы, индекс не используется повторно,
  удаление LOGIC убирает его назначения, ссылки из других BLOCK остаются,
  удалённый и повторно удаляемый сценарий дают `-32603 Not found: 'Scenario
  N'`, повторное создание сохраняет поля.
- Не совпало: ключ окна опций сценария в симуляторе `scenario-options-N`, на
  хабе — индекс; окно назначения LOGIC `Logic/<тип>/<aId>/<sId>` против
  `Logic/<тип>/<aId>.<sId>/`; `logic.list` пустого сервиса в симуляторе не
  содержит `logics`, на хабе новая виртуальная лампа сразу получает
  `LightbulbControl`; ответ назначения в симуляторе без `desc`.

## Ограничения

- Один хаб, один полный прогон, паузы чтения 0,8–1,0 с.
- Удалялись только свои сценарии. Встроенные LOGIC (индексы-слова,
  `predefined: true`) не удалялись; удаляет ли их хаб, неизвестно.
- Не проверялись: удаление во время выполнения сценария (задержка,
  `sync`), сценарий с `onStart: true` при повторном создании, удаление
  через кнопку `Remove` окна опций, событие хаба об удалении, запись в журнал
  хаба, что видит приложение SprutHub на месте висящей цели `scenario` и что
  делает BLOCK, когда срабатывает такая цель.
- Вызовы сценариев из кода LOGIC и GLOBAL и зависимость кода LOGIC от
  функций GLOBAL не исследовались: их удаление может сломать чужой код, и
  хаб этого не сообщит.
- Опции назначения LOGIC (`logic.getOptions`) до и после удаления не
  читались: назначение пробы было без опций.
- Чтение назначений по всему дому (`logic.list` каждого сервиса) заняло 28 с
  до прогона и 60 с после; в первом запуске оно оборвалось на аксессуаре,
  который исчез между `accessory.list` и `logic.list`. Тот же обход делает
  `findLogicAssignments` продукта: он бросает ошибку на первом таком
  аксессуаре.
