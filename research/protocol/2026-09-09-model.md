## Подтверждение текущей реализацией

Историческая привязка принятого на этом этапе runtime: base
`5d1372d40c4a8eb3b3a5c73f09303f9c0e885e50`, SHA-256
`src/server.mjs` —
`6733c8eab427821b15a93a8abeab0355edfe14a455b6f2088a763c9fd498f911`,
`src/spruthub-client.mjs` —
`6f33a6bfa6e0863a82f3de8bc523750445249b17116ed697ef2ce9f69d135d6b`.
Эти идентификаторы фиксируют источник наблюдения, но не задают текущую
реализацию: её определяет актуальный код.

Публичный [JavaScript-ресурс](https://beta.spruthub.ru/js/app.16735171810a795a9f2d.js)
содержит 31 извлекаемый protobuf-модуль. Существующий `extractProtoModules`
из `research/extract-spruthub.mjs` извлёк их без нового парсера. Размер ресурса
1 348 618 байт, SHA-256
`81c1ef74ce21eb5ccff583255ba82fe766ff4cf6bc251c0566b7bd67436647f8`.
Прочитаны `Accessory.proto`, `Service.proto`, `Characteristic.proto`,
`Utils.proto`; полный snapshot CLI этим наблюдением не проверен.

Текущий UI запрашивает `service.types` и `characteristic.types`. Независимые
read-only запросы к настоящему хабу подтвердили соответственно 103 и 308 типов.
[Сокращённый ответ каталога](2026-09-09-type-catalog.json) сохраняет три сервиса
и шесть характеристик мультисенсора. Остальные типы не проверялись по отдельности.

| Сущность | Нативное содержание | Наблюдаемое значение для интеграции |
| --- | --- | --- |
| Accessory | `id`, `roomId`, `services`, `online` | Устройство, принадлежность комнате, доступность. |
| Service | `aId`, `sId`, `type`, `name`, `characteristics` | Функциональная часть устройства; несколько сервисов могут иметь один тип. |
| Characteristic | `aId`, `sId`, `cId`, `control`, признаки options/links | Устойчивая ссылка относится к экземпляру; имя и тип не заменяют ID. |
| control | `type`, `name`, `value`, `unit`, read/write/events, ограничения, `validValues`, видимость | Вместе со значением передаётся его смысл и возможности конкретного экземпляра. |
| Тип сервиса/характеристики | Идентификатор типа, формат, права, единицы, enum; обязательные/опциональные характеристики сервиса | Хаб уже содержит словарь типов. Настройки экземпляра могут уточнять каталог. |
| options и links | Отдельные настройки и связи характеристики | Это конфигурация устройства, которую нельзя восстановить по одним показаниям. |

`Value` — типизированное объединение, а не только число. В датчике наблюдены
bool/int/double/string; схема также содержит long и mesh. Работа клиента с
long/mesh в этом исследовании не принималась. Получение ответа не устанавливает
время физического измерения; подходящей временной метки в выбранном ответе нет.

У `ChargingState` каталог перечисляет три режима, а экземпляр оставляет
`checked: true` только для `NOT_CHARGEABLE`. Для `StatusLowBattery` оба варианта
имеют `checked: true`. UI фильтрует варианты через `checked ?? true`.
Следовательно, `checked` здесь ограничивает доступные варианты, а не обозначает
текущее значение. Оно находится отдельно в `control.value`.

`visible`/`hidden` описывают представление в UI и не заменяют `read`/`write`.
В наблюдённом датчике невидимый `ChargingState` читается; `Identify` содержит
значение, но явно помечен `read: false`, `write: true`.
Подробности и обезличенный ответ — в [наблюдении мультисенсора](2026-09-09-motion.md).

## Установленная потеря и граница дальнейшей работы

В клиенте на `85850c944b41043b0e5db3d140efbbcef9e8d67c` нормализация сохраняет
имя/тип/значение/единицу, но отбрасывает перечисления и права; каждый control
попадает в readings. Поэтому сырой код зарядки остаётся без расшифровки,
а write-only команда выглядит как показание. Причина общая для устройств;
ветвление по модели Aqara её не устраняет.

Для компактного чтения нужны читаемое значение, исходный код и его нативный
смысл, единица, устойчивая ссылка и честная свежесть. Подробные ограничения,
допустимые варианты, возможности управления, options/links следует раскрывать
по необходимости при работе с конкретной характеристикой. Наблюдение этих
полей не требует немедленно добавлять все такие инструменты в первый срез.
Незаполненные данные нельзя заменять догадкой; неизвестный enum остаётся
неизвестным, а данные экземпляра нельзя затирать общим справочником.

Wiki описывает нативный `SwitchOffTime` для датчиков, которые сами не передают
«нет движения». Это полезное направление отладки, но фактическая настройка
таймера выбранного датчика не прочитана. Постоянное `true` в наших четырёх
чтениях не доказывает зависание или конкретную длительность этого таймера.
