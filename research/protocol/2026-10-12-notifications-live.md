# Уведомление характеристики: запись и где хаб его показывает

O20261012-notifications-live, 2026-10-12. Цель — проверить на живом хабе
запись `characteristic.update {aId, sId, cId, notify}`, которую
`characteristic_notify` взял из кода веб-клиента и схемы
([2026-09-24-web-client-action-map.md](2026-09-24-web-client-action-map.md),
B8), и узнать, какие чтения возвращают `notify`.

## Источники

- Architect, живой прогон `npm run conformance:live -- --only 1,V,N`
  12.10.2026 на доме владельца: Sprut.hub 2, прошивка 3.0.0, ревизия 20131;
  sprut-agent `d081d6f`, сервер из `dist/plugin`. Уровень `O`.
- Записи шли только в собственный виртуальный аксессуар прогона (Lightbulb
  с On, Brightness и Hue, без links) в комнате прогона. Лампу никто не
  переключал, поэтому уведомление не отправлялось.

Отчёт прогона лежит во временном каталоге вне репозитория; serial, имена и
значения дома здесь не сохраняются.

## Процедура

1. Сырые `accessory.get {id}`, `characteristic.get {aId, sId, cId}` и
   `accessory.list {expand: "services,characteristics"}` для On виртуальной
   лампы, затем `get_entity` её ref.
2. `characteristic_notify` с `true` на этом On (prepare, apply), те же
   чтения и `find_devices notify=true`.
3. `restore_native_change` (запись `notify: false`), те же чтения.
4. Те же сырые чтения для `C_Online` информационного сервиса виртуального
   аксессуара.
5. `notify` всех характеристик устройств владельца из `accessory.list` до и
   после шага.

## Наблюдение

- Запись работает: `characteristic.update {aId, sId, cId, notify: true}`
  применена, `accessory.get` вернул `notify: true`; restore записал `false`,
  `accessory.get` вернул `false`.
- `notify` есть только в `accessory.get`, и там на каждой прочитанной
  характеристике: до записи на свежем On было `notify: false`, не
  отсутствие. В `characteristic.get` и в `accessory.list` с раскрытыми
  характеристиками поля нет ни до, ни после записи, ни при `true`.
- Поэтому `find_devices notify=true`, читавший `accessory.list`, не нашёл
  включённое уведомление, а сравнение настроек владельца по
  `accessory.list` («0 из 1395 включено») ничего не доказывает: в списке
  `notify` нет вообще.
- У виртуального аксессуара есть информационный сервис: sId 1, `C_Online`
  с cId 8; сам Lightbulb — sId 13, On — cId 15. `C_Online` нового
  виртуального аксессуара имеет `notify: true` в `accessory.get` до любой
  записи. Шаг ожидал `false` и дальше по `C_Online` не писал.
- Прогон вернул всё: restore уведомления подтверждён, виртуальный аксессуар
  и комнаты удалены, финальный снимок совпал с начальным.

## Подтверждённый вывод

Настройку уведомления характеристики читать только из `accessory.get`.
Отсутствие `notify` в `accessory.list` и `characteristic.get` значит «не
прочитано», а не «выключено». Ответ на «какие уведомления включены» требует
`accessory.get` для каждого аксессуара, о котором вопрос. Исходное значение
для возврата тоже берётся из `accessory.get`: у `C_Online` нового
виртуального аксессуара это `true`, а не `false`.

## Ограничения и неизвестные

- На физических устройствах владельца `accessory.get` с `notify` не читали:
  есть ли поле на каждой их характеристике и какое значение у `C_Online` по
  умолчанию, не проверено.
- Через какие службы уведомлений и кому хаб отправляет такое уведомление,
  не наблюдали.
- Сколько стоит `accessory.get` для каждого аксессуара дома и выполняет ли
  хаб параллельные запросы одного соединения параллельно, не измеряли.
