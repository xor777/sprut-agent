## Текущий официальный клиент и схема

Официальный `https://beta.spruthub.ru/` в день проверки отдавал
`app.16735171810a795a9f2d.js`, SHA-256
`81c1ef74ce21eb5ccff583255ba82fe766ff4cf6bc251c0566b7bd67436647f8`.
Его `VirtualMainScreen` отправляет:

```text
accessory.create({
  name,
  roomId,
  services: [{type, name, optional}]
})
```

Для выбранной виртуальной характеристики `CharacteristicLinksScreen` добавляет
входящую связь вызовом:

```text
link.addVirtual({aId, sId, cId, tAId, tSId, tCId})
```

Здесь первая тройка относится к виртуальной характеристике, `t*` — к реальной.
После изменения списка UI отправляет `characteristic.update` с `hasLinks`.
Выбор режима — отдельный `characteristic.update` с `linkProcessing`; UI считает
отсутствующее значение новым `LastValue`. В клиентском enum `LastValue = 0`,
`MaxValue = 1`, `Sync = 2`, `MinValue = 3`, `MidValue = 4`. Поэтому реализация
проверяет у созданных характеристик эффективное значение 0 и не объединяет два
UI-действия в неподтверждённый составной payload.

Встроенная текущая protobuf-схема подтверждает `AccessoryCreateRequest` с
`services: ServiceCreateRequest`, ответ `AccessoryMessage`; для links —
`LinkAddVirtualRequest` и ответ `LinkMessage`, удаление аксессуара —
`AccessoryDeleteRequest` и пустой ACK. `ServiceCreateRequest.optional` содержит
типы дополнительных характеристик. Каталог допустимых required/optional типов
читается отдельным `service.types`, поэтому реализация не угадывает состав
`Lightbulb` по архивной схеме.

Официальная [Wiki о links](https://wiki.spruthub.ru/%D0%A1%D0%B2%D1%8F%D0%B7%D0%B8_%D0%BC%D0%B5%D0%B6%D0%B4%D1%83_%D0%B2%D0%B8%D1%80%D1%82%D1%83%D0%B0%D0%BB%D1%8C%D0%BD%D1%8B%D0%BC%D0%B8_%D0%B8_%D1%80%D0%B5%D0%B0%D0%BB%D1%8C%D0%BD%D1%8B%D0%BC%D0%B8_%D1%83%D1%81%D1%82%D1%80%D0%B9%D1%81%D1%82%D0%B2%D0%B0%D0%BC%D0%B8_%28%D0%9B%D0%B8%D0%BD%D0%BA%D0%B8%29)
задаёт ту же направленность: связь на виртуальном устройстве входящая, на
реальном исходящая. Для нескольких ламп с обратной связью рекомендовано
`Последнее значение`; `Синхронизация` может разнести промежуточное значение на
остальных участников.

## Фактические границы текущего дома

Read-only проверка Architect в SPRUT-39 установила общий пересекающийся набор
двух выбранных ламп: `On` и `Brightness` 0–100 с шагом 1. Только одна лампа
имеет `ColorTemperature`; `Hue` и `Saturation` нет у обеих. Существующая
виртуальная группа на том же хабе уже использует IN-links `On/Brightness`, её
нельзя менять или использовать как созданный продуктом объект.

Поэтому публичная операция принимает точные service refs и явные
`On/Brightness`, заново читает оба аксессуара и `service.types`, создаёт только
один виртуальный `Lightbulb` и связывает только эти две характеристики. Она не
выводит управляющие характеристики из диагностических или служебных полей.

## Live-наблюдение и ограничения

Отдельный разрешённый live-опыт Architect подтвердил `accessory.create` на
SprutHub 3.0.0: ответ вернул однозначный ID созданного virtual accessory, а хаб
обрезал длинное имя до 30 символов. Поэтому подтверждённый ответ сохраняет право
удаления по ID, а публичный результат различает requested и observed name.
Второй короткий опыт подтвердил на SprutHub 3.0.0 четыре `link.addVirtual` и
`link.list`: виртуальные On/Brightness получили IN-связи к соответствующим
характеристикам двух выбранных ламп. Новое значение виртуальной яркости дошло до
обеих. После ручной установки одной лампы в 10% вторая сохранила 30%, а
виртуальная обратная связь стала 10% — наблюдаемое поведение `LastValue`
соответствует ожидаемой несинхронизирующей семантике.

Повторная запись уже отображаемых виртуальных 10% получила ACK, но ближайший
readback остался 10%/30%. Текущая схема `CharacteristicUpdateRequest` и UI
отправляют тот же `control.value` без признака force; подтверждённого нативного
способа заставить хаб повторно разослать равное значение не найдено. Поэтому
продуктовый characteristic change для собственной группы проверяет readback
каждого участника и сообщает `group_members_not_converged`, а не успех по одному
virtual scalar. Он не добавляет отдельную синхронизационную автоматику.

Первый live-возврат удалил accessory до удаления IN-links. После этого на четырёх
физических характеристиках остались отсутствовавшие в baseline пустые OUT
`Virtual/...`; адресный `link.remove` на уже пустом физическом OUT вернул ACK, но
не убрал контейнер. Актуальный UI при удалении входящей связи сначала вызывает
`link.remove` на виртуальной характеристике и её IN index, затем обновляет
`hasLinks`. Реализация повторяет этот порядок, проверяет исчезновение сохранённых
физических OUT и не удаляет accessory при остатке. Этот исправленный порядок ещё
не воспроизводился live.

Синтетический WebSocket-тест проверяет точные JSON payload, последовательный
журнал, readback, потерянные ответы, физические counterpart links и безопасное
удаление. Потерянный create нельзя считать своим по одному похожему кандидату.

Статическое чтение клиента и первоначальные факты об устройствах не меняли дом.
В разрешённых live-опытах временные virtual accessories удалены; активные targets
пустых OUT отсутствовали, physical values/options и сценарии восстановлены.
Идентичность link baseline после ошибочного порядка удаления не была подтверждена
на момент снимка; дальнейшая очистка и приёмка остаются у единственного live
writer. Датчики не изменялись.
