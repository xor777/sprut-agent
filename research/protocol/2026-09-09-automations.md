# Нативные механизмы автоматизации

Read-only исследование 2026-09-09 на Sprut.hub 2, `3.0.0b (20131)`.
Текущий frontend и его hash указаны в [карте модели](2026-09-09-model.md).
[Проекция ответов](2026-09-09-automation-context.json) обезличена и сокращена.
Применение, запуск или удаление сценария в этом исследовании не выполнялись.

## Что подтвердилось

- `scenario.list {}` вернул 19 объектов: пользовательские BLOCK/GLOBAL/LOGIC
  и встроенные LOGIC с `predefined: true`. Каталог не содержал `data`.
- `scenario.get {index, expand: "data"}` вернул строку JSON для BLOCK с
  `blockId`, `targets`, вложенными условиями и действиями. Сохраняются реальные
  `aId/sId/cId`, а также `hs/hc`. Прочитанный сценарий сопоставлен с нативным
  редактором: временной интервал, условие характеристики, ветки then/else.
- `scenario.sdk {}` вернул актуальные декларации API сценариев прямо с хаба:
  38 010 байт, SHA-256
  `1c54e25f642e8cc82cd774db7ea40f3f9c610d0ec28b78904172d08be085ad6d`.
  Есть Hub, Accessory, Service, Characteristic, Room, HTTP, Cron и другие
  интерфейсы. Это первичный источник для кода на хабе, не внешний транспортный SDK.
- `scenario.list {aId}` для выбранных источника и лампы вернул пустые объекты
  результата. Это отсутствие прямых записей в ответе, не доказательство
  отсутствия зависимостей внутри произвольного кода.
- `logic.list {aId,sId}` у лампы вернул активную `LightbulbControl`
  («Связь включения и уровня»), которая не является отдельным пользовательским
  BLOCK-сценарием. У выбранного датчика список пуст.
- `logic.types {aId,sId}` зависит от сервиса. Для лампы доступны также
  AdaptiveLighting, LightInTime и SmoothBrightnessChange; для датчика —
  MotionDetectedFromCurrentMotionLevel. Их наличие не означает, что они назначены.
- `link.list {aId,sId,cId}` для обеих выбранных характеристик вернул SYSTEM
  связи с контроллером. Свойств, подтверждающих виртуальную связь между ними,
  в этих ответах нет.
- `characteristic.getOptions` подтвердил у датчика `SwitchOffTime = 180` секунд.
  Это настройка сброса его собственного состояния; она сама по себе не является
  правилом включения другой лампы.
- `extension.list {}` различает установленные CONTROLLER, BRIDGE, NOTIFICATION
  и PLUGIN, их enabled/state. Чтение параметров модулей, установка и изменение
  не выполнялись. Состояние модуля и наличие типа — разные факты.

## Ограничения источников

В текущем `Scenario.proto` перечислены BASIC/CODE/BLOCK/LOGIC/TEMPLATE/SMART/
GLOBAL/SKILL. Наличие enum не подтверждает возможность создавать каждый тип;
живое чтение проверено для указанных выше объектов.

Текущий `Bundle.proto` прямо помечает RPC `bundle.*` удалёнными и указывает на
appstore. Старый снимок схем не годится как обещание рабочего каталога модулей.
Вызовы `bundle.*` не выполнялись. Для состава установленного использован
проверенный `extension.list`.

JSON Schema в веб-клиенте описывает блоки, но не является точной схемой сохранённого
`data`: например, живой ответ содержит `blockId`, которого нет в соответствующей
схеме с `additionalProperties: false`. Нельзя отвергать наблюдённый ответ только
из-за такого валидатора. Проверенный обмен важнее предположения о назначении схемы.

## Ближайший срез

Для пользовательского «движение → включить лампу» исследованы отдельные источник
MotionSensor/MotionDetected и цель Lightbulb/On. Существующая логика лампы
сохраняется. Один BLOCK с условием true и действием set true представляет
этот результат в нативном редакторе. Автовыключение в поручение не входит.
Обоснование выбора и правила против дублирования должны получать внешние агенты
через продукт, а не только разработчики через AGENTS.

Для восстановления новой автоматизации нужен журнал владения созданным объектом
и проверка его текущего состояния перед удалением. Наличие create/update/delete
в protobuf ещё не подтверждает применение или откат; это предмет живой приёмки
следующего среза. Предварительная проверка изменений не даёт атомарный CAS,
которого в прочитанной схеме запросов нет.
