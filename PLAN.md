# Рабочая стратегия

Текущее состояние, следующие шаги и действующие решения. Целевой продукт — в
[VISION.md](VISION.md), что уже работает — в [README.md](README.md), история
изменений и проверок — в Git. Разборы возвратов волн 3–4 —
[research/archive/2026-10-plan-decisions.md](research/archive/2026-10-plan-decisions.md).

## Как ведётся работа

- Волна — несколько связанных результатов. Каждый проходит разработку,
  независимое ревью свежим агентом, eval на настоящей модели, где меняется
  поведение агента, и живую проверку на хабе, где меняется запись. Исполнители и
  ревьюеры — субагенты Claude на Opus; правила — в [AGENTS.md](AGENTS.md).
- Усилие по ценности для дома. Редкий сбой (потерянный ответ, переподключение)
  получает честное «неизвестно, проверь»; после одной правки и одного ревью
  оставшийся редкий случай записывается как ограничение, а не чинится новым
  кругом.
- Eval расходует подписку владельца: только кейсы, которые затрагивает изменение,
  по одному прогону, субагентом на Sonnet с инструментами на симуляторе, а не на
  настоящем доме. Полный прогон — только по его просьбе.
- Поверхность для агента — бюджет: число инструментов, длина инструкций и
  описаний, результат Sonnet в eval. Новая возможность по умолчанию не
  добавляет инструментов.
- Живые проверки: читать можно всё; создавать только свои временные объекты и
  сразу удалять; свои сценарии можно запускать, если они действуют только на
  временные виртуальные устройства; настоящие устройства, сценарии и настройки
  дома — только с подтверждения владельца. Выпуск на GitHub — по согласованию.

AX идёт через все волны:

- Мера: классы провалов eval, MCP-вызовы и байты на задачу; Sonnet — рабочая
  планка. Перед первой правкой AX — 5–6 кейсов по одному прогону.
- Правила переносятся из текста в ответы сервера: сначала имена, а не номера;
  `tell_owner` вместо правки устаревшего описания; поиск перечисляет кандидатов
  при неоднозначности.
- Запись короче: если `prepare_native_change` при неверных полях возвращает
  правила операции, отдельный контракт не нужен. Решает замер.
- В каждом отказе следующий шаг; истёкшая сессия и неверный пароль — кейсы eval.
- Настоящий провал из журнала работы становится кейсом eval.

Не делаем: развитие голоса сверх эксперимента, новые клиенты и дашборды, пробелы
BLOCK без реальной просьбы, рефакторинг без конкретной поломки, углубление редких
сбоев. «Сцена с кнопкой целиком» — один eval-кейс без новой разработки.

Голос владелец делает в отдельной сессии; исследование платформ —
[research/voice/2026-10-13-realtime-tools.md](research/voice/2026-10-13-realtime-tools.md).

Позже: приложение «История» из магазина хаба и `history.list` ([наблюдение](research/protocol/2026-11-07-history-app.md) — требует внешнюю SD-карту, отложено владельцем 25.11.2026); обслуживание (проверка связи, лечение, прошивка — с подтверждением).

Известные мелочи: шаблон Wi-Fi QR квадратичен на длинном тексте; поле
`Ticket` окна Xiaomi покажет одноразовый код; поиск устройств при сбое записи
состояния говорит «сеть не открыта»; LOGIC с секретом в
коде агент переименовать не может. Снимок дома: до первого события соединения каждый
ответ читает дом целиком, полное чтение дочитывает связи виртуальных ламп
(~250 мс на 9 групп), и событие, которое снимок не может применить, пришедшее
за это время при повторном полном чтении, отбрасывает чтение целиком;
`get_entity` показывает группы лампы только по свежему снимку; связи,
изменённые в приложении, видны не позже чем через 5 минут; старое полное
чтение, закончившееся позже нового, может на миг показать прежнее значение
записи. Отмена: после потерянного ответа и неудачного чтения отмены команды
устройству предлагается повтор без нового чтения; подтверждённая хабом более
новая команда без нового значения в чтении считается не применённой; отмена
удаления сценария создаст вторую копию, если владелец уже создал его сам.
Код: `hub_code_error` ловит только компиляцию и верхний уровень при записи,
ошибка внутри функции видна лишь в журнале при запуске сценария; методы
отклоняются по имени и у собственных объектов кода; поиск зависимостей кода
смотрит первые 24 сценария с кодом. Вход: каждый процесс MCP входит сам, при
одновременных отказах не больше одного входа на процесс; `TOO_FAST` без задержки не
выжидается (5 вызовов дают 5 `account.auth`, пароль не уходит); `connection_changed`
приходит только при отказе сессии. Журнал: каталог конфигурации только для чтения
залипает до перезапуска; процесс, остановленный дольше двух минут и продолживший
работу, может заменить статус `restored` на `uncertain` при верном доме; часы вперёд
больше чем на 100 секунд могут забрать живую блокировку. Оборванное изменение (всё
воспроизведено на симуляторе, дом не портится): в пакетной отмене нет кандидатов при
незаписанном id, их показывает `get_native_change`; потерянная до хаба настройка группы
света даёт `manual_change` вместо «неизвестно», выход `virtual_device_delete`, агенту
его никто не подсказывает; повтор завершённой отмены при занятой блокировке говорит о
частичном результате, следующий вызов отвечает `restored`; среди кандидатов группы
может оказаться новая лампа другого изменения; отказанное создание после отмены
становится «неизвестным», выход новый prepare. Встроенные сценарии: встроенный BLOCK
на настоящем хабе не наблюдался, только в фикстуре; пустая правка встроенного BLOCK
остаётся `prepared`; цель, перенесённая в другую ветку BLOCK, считается новой.
Мосты: что видит приложение ассистента, с хаба не наблюдается.

## Действующие решения

- Цель — замена интерфейса, а не покрытие методов хаба: операция добавляется,
  когда без неё владельцу приходится открывать интерфейс.
- Неизвестный внешний контракт проверяется на хабе, а не угадывается.
- Правила поведения агента — в инструкциях сервера (не длиннее 2048 символов,
  главное в первых 512), правила инструмента — в его описании (до 1000).
- Истёкший запрос выводит из обращения только своё соединение; соседние
  запросы не теряют ответ.
- Поиск устройств хранится в каталоге состояния и переживает перезапуск
  сервера; новое — только ребёнок контроллера не из своих «до».
- Подпись со словом-секретом скрывает любое значение, кроме «да/нет».
- Отмена команд не возвращает яркость ламп со связью «включение и уровень»:
  запись уровня выключенной лампе её включает.
- У LOGIC имя, описание и запуск при старте меняются только через `info` в
  коде: хаб берёт их оттуда при каждой записи кода.
- Голос — отдельный слой поверх общего ядра; в сервере нет ничего
  специфичного для одной платформы.
- Голосовой стенд остаётся в Москве: OpenAI отклоняет запросы из региона,
  поэтому выход к нему идёт через VLESS к польскому серверу, а российские
  адреса и SprutCloud — напрямую.
- Свежесть снимка дома — один счётчик поколений: чтение, во время которого
  пришло неприменимое изменение, не используется.
- Неудачное чтение не ведёт ни к записи, ни к окончательному выводу: исход
  остаётся неизвестным с предложением повторить.
- Мостами (Алиса, HomeKit и другие) агент управляет по просьбе владельца
  (14.10.2026): включает и выключает в них конкретные устройства — после
  проверки записи экспорта на хабе.
- Перевязка групп ламп (23.10.2026, два возврата, бюджет исчерпан). Продукт
  давал состав группы, но не давал опознать замену; попытка вывести
  «кандидатов» и «новой лампы на хабе нет» дала ложные утверждения (лампа в
  другой комнате, белая вместо цветной). Решение владельца: чтения дают
  факты — состав группы, группы лампы с комнатой, свободные лампы комнаты и
  чего им не хватает — без выводов; `get_entity` не читает ради пометок весь
  дом. То, что Sonnet иногда открывает подключение нового устройства, —
  ограничение, без нового круга.
- Результат подготовки называет следующий вызов `apply_native_change`, когда
  запрос просит само изменение; когда владельцу сначала нужно что-то сказать,
  результат несёт `tell_owner` и следующего вызова не даёт (23.10.2026: без
  этого Sonnet готовил верное изменение и переспрашивал).
- Виртуальные устройства, второй возврат (23.10.2026). Исправление ревью
  включило непрочитанный код (`code_unread`) в зависимости, и одна проверка
  стала решать два разных вопроса: «сказать владельцу перед удалением» и
  «запретить отмену своего создания». В доме больше 24 сценариев с кодом
  отмена своего свежего устройства всегда отвечала «используется». Решение:
  отмену своего создания останавливают только найденные ссылки; непрочитанное
  называется в результате, но не запрещает. Сохраняется: найденную ссылку
  отмена не ломает, удаление по просьбе при любой зависимости или неизвестности
  сначала говорит владельцу. Один цикл «исправление → ревью».
- Удаление по просьбе (сценарий, виртуальное устройство): без найденных
  зависимостей — без вопроса; при найденной зависимости или неизвестности —
  сначала владельцу (`tell_owner`); отмена создаёт объект заново под новым
  номером или id и называет, что не вернулось. Физические устройства агент
  пока не удаляет (23.10.2026).
- Кнопки окон устройств отложены (23.10.2026, PM и чтение 96 окон дома): у
  владельца нет лечения, проверки связи и прошивки, смысл «Переспарить» не
  установлен, «Удалить все аксессуары» хаб выполняет без подтверждения, а
  упоминания устройств в коде GLOBAL тогда не были видны (с 09.11.2026 видны id в
  списках чисел) — удаление устройства молча сломало бы сцены. Первой будет «удали устройство из сети» с одним
  вопросом, после видимости id в коде.
- Тесты изолированы от настоящего дома: временный `HOME`, без переменных
  подключения, соединения только на локальные адреса (23.10.2026: новый тест
  без явного подключения прочитал бы учётные данные владельца).
- Порядок работы над основным инструментом (06.11.2026, выбор владельца):
  надёжность, затем функции, AX через все волны; голос — эксперимент. Причина:
  после смены пароля инструмент на Mac молча перестал работать, журнал изменений
  на этом Mac с 18.09 получил одну запись, а 7 проверок с владельцем не пройдены.
- Журнал после отправленных шагов, второй возврат волны 1 (06.11.2026). Первая
  правка убрала ложное «ничего не отправлено», но по брифу Architect не терять id
  созданного хабом объекта держала запись в памяти процесса и дописывала её
  таймером. Ревью воспроизвело: эта запись затирает законченную запись другого
  диалога, и отмена отвечает «изменили руками», хотя дом верный. Причина в
  постановке: у редкого сбоя (журнал занят дольше 15 секунд ровно после шага) уже
  был честный путь, исход неизвестен, как при потерянном ответе. Сверка версий при
  дозаписи оставила бы вторую копию журнала и добавила состояния. Решение: копии в
  памяти нет, журнал остаётся единственным местом; созданное, чей id не записан,
  агент называет и своим не считает. Сохраняется: когда шаги ушли, ответ не говорит
  «ничего не отправлено», даёт `hub_effect` и следующий вызов; повтор сначала
  сверяется с хабом и не шлёт сработавшее; отмена не трогает чужое. Этим же циклом:
  тот же ложный ответ при сбое чтения сразу после шага (одно место для всех причин
  остановки) и сбои чтения журнала и точек конфигурации вместо `internal_error`.
  Один цикл «исправление → ревью». Итог: прогоны с остановкой на каждом шаге и двумя
  диалогами закрыли эти классы (на прежней версии 34 из 100 прогонов с нарушениями,
  здесь ни одного, кроме описанного ниже). Бюджет возвратов исчерпан. Результат принят;
  оставшиеся случаи редкого сбоя не портят дом и записаны в известных мелочах, отдельно
  стоят пакетная отмена без кандидатов и `manual_change` при потерянной настройке.
- Цели BLOCK (06.11.2026): новая цель на встроенный сценарий и новая запускающая
  цель на GLOBAL отклоняются до записи; стоящие в сценарии цели при правке и отмене
  остаются, иначе нельзя было бы править сценарии, сделанные в приложении SprutHub.
- Ночная проверка не ставится без решения владельца (06.11.2026). Перед установкой
  решить: молчание значит и «всё хорошо», и «проверка умерла»; реквизиты только из
  окружения не доходят до launchd; без `node_modules` она падает молча; `delivered:
  true` значит только код выхода 0; при открытых правах `session.json` совет ведёт к
  `connection.env`.
- `evidence.live_hub_version` в контрактах называет прошивку, на которой наблюдалось
  само действие, а не последнюю проверенную (06.11.2026): конформанс этих действий не
  покрывает, новая прошивка их не подтверждает.
- История сначала без установки (07.11.2026). `lastUpdate` уже есть на хабе, он
  бесплатен и ничем не рискует, хотя отвечает только за последнее сообщение. Своя запись
  событий на Mac отклонена: нужен постоянно работающий сервис и настроенная подписка,
  а штатное приложение уже есть. Ставить бету на настоящий хаб решает владелец.
- Второй возврат по `last_report` (07.11.2026). Ревью на `37c7846` существенного не
  нашло, но eval нашёл: на «почему вчера выключился свет», когда сценарий подходит по
  времени, агент прочитал журнал и настройки сценария, а времени последних сообщений не
  посмотрел. Ответ честный, но без единственного факта, который хаб знает; на `2f81d39`
  тот же кейс его смотрел, значит возможность находится случайно. Причина в постановке,
  а не в реализации: принимали инструмент, а дорогу к нему оставили концу описания
  `find_devices`. Журнал, куда агент идёт первым, говорит «раньше событий нет» и на этом
  обрывается. Упрощения не нашлось: оставить только `last_report_at` в `get_entity`
  значит увести факт ещё дальше от агента, а показывать его в каждом `find_devices`
  стоит чтения каждого устройства. Фраза в инструкциях сервера дешевле, но правила мы
  переносим из текста в ответы. Поэтому журнал, прочитанный целиком, называет вызов для
  более раннего времени отдельным полем, а не `next`: инструкции велят следовать `next`,
  а вопрос об ошибках в журнале не должен читать весь дом. Сохраняем: время сообщения не
  выдаётся за время выключения, ничего не записывается, журнал сам лишних чтений не
  делает. Конечная проверка: по одному прогону `why-lights-off-yesterday`,
  `why-lights-off-no-scenario` и `log-diagnosis`. Если агент и так не находит, правок
  дальше не делаем: сообщаем владельцу и решаем, принимать ли без этого.
  Итог: не нашёл. Поле `earlier_times` агент прочитал в обоих вопросах про гостиную и
  времени не посмотрел, а в `log-diagnosis` пересказал его как «по лампам этого не
  определить». Возможная причина, не проверенная: наши тексты говорят, чего это время не
  доказывает, и не говорят, зачем оно нужно. Бюджет исчерпан, поэтому в `main` влито
  полезное само по себе, `last_report` и `last_report_at` до `37c7846`; поле осталось в
  ветке `feat/device-last-report` (`9f604bb`), его ревью дефектов не нашло, но оно
  утяжеляет каждое чтение журнала без показанной пользы. Пределы группы `reported_together`
  записаны в [наблюдении](research/protocol/2026-11-07-history-app.md).
- Id в списках кода (09.11.2026). Число, равное id устройства, считается упоминанием,
  если оно стоит в массиве из одних чисел, а тот же код вызывает метод `Hub` с id
  не числом, то есть ищет устройства во время работы. Числовые переменные не
  считаются: на доме владельца `CH_ON` и подобные держат номера характеристик,
  совпадающие с id устройств, и дали бы ложные упоминания. Код, который парсер не
  разобрал, называется в `unchecked` как `not_parsed`, а не читается как «упоминаний
  нет». Один возврат с ревью: переполнение стека на очень длинном коде ломало связи
  всех устройств, исправлено. Пределы: случайное совпадение числа в таком массиве
  останавливает отмену своего виртуального устройства, выход — удаление по просьбе;
  пункт пакетной отмены не называет зависимости, их видно в `get_native_change`;
  неразобранный код добавляет вопрос владельцу к каждому удалению виртуального
