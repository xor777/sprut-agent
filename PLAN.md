# Рабочая стратегия

Текущий шаг, основания приоритетов, следующие шаги и принятые решения. Целевой
продукт — в [VISION.md](VISION.md), что уже работает — в [README.md](README.md).
Отдельного трекера задач нет: ход работы — в этом файле и в истории коммитов.

## Как ведётся работа

- Работа идёт волнами. Волна — несколько связанных результатов, каждый проходит
  разработку, независимое ревью свежим агентом, eval на настоящей модели, где
  меняется поведение агента, и живую проверку на хабе, где меняется запись.
- Исполнители и ревьюеры — субагенты Claude на Opus. Правила разработки, ревью и
  Git — в [AGENTS.md](AGENTS.md).
- В конце волны этот файл обновляется: состояние, решения волны, следующие шаги.
  Выпуск на GitHub — по согласованию с владельцем.
- Живые проверки: читать можно всё; создавать только свои временные объекты и
  сразу удалять; свои сценарии можно включать и запускать, если они действуют
  только на временные виртуальные устройства прогона; настоящие устройства,
  сценарии и настройки дома — только с подтверждения владельца.

5. Переименование сценариев всех типов через окно опций.

Мелкие остатки ревью: без blockId сопоставление правил решает, какие узлы
считаются сохранёнными, и может отказать в слиянии — сказать об этом в контракте;
кэш сравнения правил для больших BLOCK. Скрытие секретов: шаблон Wi-Fi QR
работает за квадратичное время (8 с на тексте 160 КБ из повторов `WIFI:;`, на
текстах хаба владельца — миллисекунды), ограничить длину сегментов; имя
настройки с частью-флагом и числовым значением отменяет проверку подписи
(«Mode» с подписью «Password» показывается); поле `Ticket` окна Xiaomi во время
входа в облако покажет одноразовый код. Соединение: нет тестов на то, что
испорченный кадр на выведенном соединении не роняет запросы нового, и на исход
наблюдения при таймауте keepalive (`connection_lost`; тест идёт около 34 с).
Поиск устройств: при уже идущем поиске и сбое записи состояния ответ говорит
«сеть не открыта», хотя она открыта прежним поиском; сбой записи после
отправленного старта отвечает `internal_error`; нет теста на сбой записи при
очистке старых наблюдений.

## Решения

- **Голосовой стенд остаётся в Москве (13.10.2026).** OpenAI отклоняет прямой
  запрос с московской ВМ с `unsupported_country_region_territory`. По выбору
  владельца установлен VLESS-клиент к существующему польскому серверу:
  российские домены и IP идут напрямую, остальной TCP/UDP — через Польшу.
  Серверы действующего VPN не менялись. Это сохраняет прямое соединение с
  SprutCloud и не требует переезда стенда. Независимое ревью устранило запуск
  voice при сбое маршрутизации; живая проверка выявила недостающий capability
  для UDP DNS. Проверены восстановление клиента, UFW reload и перезагрузка.

- **Цель — замена интерфейса, а не полное покрытие методов хаба.** Операция
  добавляется, когда без неё владельцу приходится открывать интерфейс.
- **Неизвестный внешний контракт проверяется на хабе, а не угадывается.** Три
  цепочки правок остановились на втором возврате ревью и сменили подход:
  оценка ответов регулярками → LLM-судья по рубрике с цитатой; классификация
  устройств по именам → нативные типы и структура аксессуара; эвристика типа
  LOGIC → номер сценария, найденный живой пробой.
- **Правила поведения агента — в инструкциях сервера.** В 93 прогонах eval агент
  не открыл skill ни разу; skill — необязательная справка. Инструкции не
  длиннее 2048 символов (12.10.2026): Claude Code до 2.1.295 режет их на этой
  длине, и все правила после неё агентам не доходили; главное — в первых 512
  (совет Codex), правила одного инструмента — в его описании, не длиннее 1000.
- **Подписи предпросмотра правки BLOCK без blockId приблизительны.** Записываемые
  данные от них не зависят: узел сохраняется только при совпадении канонической
  формы.
- **Чтение пояса хаба не зависит от срока вызвавшего запроса.** Фоновое
  обогащение не должно рвать общее соединение.
- **Таймаут одного запроса не должен рвать общее соединение (12.10.2026).**
  Класс повторился трижды: чтение пояса хаба с коротким сроком, затем со
  сроком вызвавшего, затем обновление каталога на исчерпанном сроке ответа
  об уведомлениях. Каждый раз истёкший запрос закрывал общее соединение, и
  параллельные вызовы, включая записи, теряли ответ. Причина — политика
  клиента: истечение срока одного запроса считается потерей связи. Решение:
  истекший запрос отменяется сам по себе, поздний ответ отбрасывается по id,
  а мёртвое соединение распознаётся отдельно. Точечные правки сроков больше не
  делаются.
- **Живость соединения не угадывается по входящим кадрам (12.10.2026).**
  Первая реализация решения выше заменяла соединение после таймаута, только
  если с момента отправки по нему не пришло ни одного кадра. Ревью показало
  дыру: хаб владельца сам шлёт события каждому сокету (около 35 за 120 с), так
  что соединение, переставшее отвечать на запросы, почти никогда не считалось
  мёртвым и не заменялось до перезапуска сервера; 0.3.0 заменял его после
  первого таймаута. Тесты этого не видели: подставной хаб событий не шлёт.
  Бюджет цикла исчерпан, владельцу сообщено. Выбрано упрощение вместо новой
  эвристики: любой истёкший запрос выводит своё соединение из обращения, новые
  вызовы идут в новое, уже отправленные в старое ждут своих сроков, после них
  старое закрывается. Сохраняются: таймаут одного запроса не обрывает соседние,
  поздний ответ отбрасывается, следующий вызов после таймаута получает ответ.
  Подставной хаб получает режим с событиями, как настоящий. Если после этого
  цикла останется существенный дефект, вернуть поведение 0.3.0 и не
  продолжать правки.
- **Поиск устройств переживает перезапуск MCP-сервера (12.10.2026).** Второй
  возврат по сопряжению. Первое ревью дало мелкие правки; затем eval на Opus
  5.5 с ответом владельца вторым ходом: агент сказал «переведите датчик в режим
  сопряжения и напишите мне», а на втором ходу получил
  `device_search_not_found`. Клиент запускает MCP-сервер заново на каждый ход,
  а поиск жил только в памяти процесса; новый старт брал устройства «до» уже
  с подключившимся датчиком и сообщал «новых нет». Причина — в постановке
  архитектора: я счёл процесс сервера живущим весь разговор, хотя физический
  шаг человека естественно разрывает ход, а клиенты-боты показывают текст
  только в конце хода. Повторное ревью того же раунда нашло вред от двух
  догадок первого исправления: устройства «до» наследовались от прошлого
  поиска без срока, и устройство, подключённое владельцем в приложении,
  выдавалось агенту как новое (P1); «не добавлено» через 20 с после конца
  объявлялось, пока хаб ещё показывал подключение (P2). Обе догадки закрывали
  ненаблюдавшиеся случаи. Упрощение без состояния не нашлось: у детей
  контроллера нет времени появления, а перечитывать окна всех детей дорого.
  Выбрано: наблюдение поиска (контроллер, действие, конец, устройства «до»)
  хранится в каталоге состояния рядом с журналом и читается по `search_ref`
  в любом следующем процессе; новое — только ребёнок не из своих «до», и
  ссылка продолжает показывать его после конца; наследование между поисками и
  срок «не добавлено» убираются, исход устройства берётся из его статуса и
  ошибки на хабе. Сохраняются: повторный старт не отправляется во время
  поиска, ZLL не запускается, стоп только своего поиска, истина — список детей
  контроллера. Новое устройство по просьбе «добавь датчик» получает понятное
  имя: имя-модель хаба не выбрано владельцем. Конечная проверка — eval
  `add-leak-sensor` с ответом владельца вторым ходом на обоих домах, затем
  живая проверка с согласия владельца. Если после этого цикла останется
  существенный дефект, сообщить владельцу и выбирать между перепроектированием
  и поставкой одного запуска и остановки поиска.
- **Поиск устройств принимается с честным текстом вместо новой эвристики
  (12.10.2026).** Ревью ограниченного цикла: сохранение между процессами и
  безопасность сети держатся, eval `add-leak-sensor` 6 из 6 на обоих домах.
  Остался P2 того же класса «что считать новым»: старая ссылка после конца
  поиска показывает и устройство, добавленное иначе (владельцем в
  приложении), а подсказка велит назвать и перенести его, утверждая
  ненаблюдавшееся «хаб называет его моделью». Времени появления у хаба нет,
  поэтому ограничивать список снова догадкой нельзя. Решение (бюджет исчерпан,
  владельцу сообщено): не перепроектировать, а исправить только текст —
  устройство после конца поиска могло быть добавлено иначе; переносить и
  называть только то, о чём просьба; имя и комнату, данные владельцем, не
  трогать; при сомнении спросить. Плюс тест на то, что старт без записанного
  наблюдения не отправляется. Ограничения: повторный старт вместо чтения
  ссылки во втором ходе теряет подключившееся устройство; правило «чужой
  поиск» зависит от часов машины и хаба; как хаб называет новый аксессуар,
  покажет живая проверка 2.

  GitHub сразу выпускает новую версию пользователям.
