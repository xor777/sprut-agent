# Разработка

Нужны Node.js 24.11+, npm и Git. Общая проверка не требует Codex:

```sh
git clone https://github.com/xor777/sprut-agent.git
cd sprut-agent
npm ci
npm run check
```

`npm run check` собирает поставляемый комплект в `dist/plugin`, проверяет, что
он совпадает с закоммиченным, прогоняет Biome и офлайн-тесты публичных MCP и
SDK входов. Внешняя граница тестов — локальный WebSocket-хаб той же формы, что
настоящий; живая проверка SprutHub в неё не входит.

## Запуск из checkout

Корневой `.mcp.json` запускает собранный комплект, когда клиент стартует из
корня репозитория. Из другой папки передай клиенту абсолютный путь
`/absolute/path/to/sprut-agent/dist/plugin/dist/server.mjs`. Эквивалентная
команда:

```sh
cd /absolute/path/to/sprut-agent
node ./dist/plugin/dist/server.mjs
```

Комплект `dist/plugin` хранится в Git и собирается заново командой
`npm run build:plugin`. `package.json` — единственный источник версии
поставки; манифесты клиентов и marketplace обновляет та же сборка.

Внутри комплекта три описания одного MCP-сервера, потому что клиенты
по-разному разрешают пути. `.claude-plugin/plugin.json` и корневой `.mcp.json`
используют `${CLAUDE_PLUGIN_ROOT}`: так читают Claude Code, Grok и адаптер MCP
для Pi, они раскрывают переменную и запускают процесс из папки сессии.
`.codex-plugin/mcp.json` использует `./dist/server.mjs` с `cwd: "."`: Codex
запускает процесс из папки плагина.

## Проверки

```sh
npm run check              # Сборка комплекта, Biome и офлайн-тесты
npm run test:codex-install # Установка плагина реальным Codex CLI 0.154.0+
npm run test:mutations     # Необязательная адресная диагностика Stryker
```

Проверка установки Codex отдельная: без CLI команда завершается ошибкой, а не
пропуском. Она ставит плагин в изолированный профиль и проходит сценарии
установки, занятого имени MCP и перехода с прежнего ручного skill.

`eval:spruthub-master` — прогон переносимого skill вместе с MCP через Codex
CLI и его профиль:

```sh
npm run eval:spruthub-master
npm run eval:spruthub-master -- contact-option plugin
```

Запуск использует временный профиль, синтетический хаб и сохраняет
доказательства вне репозитория. Успешный выход подтверждает завершение прогона,
а не продуктовый вердикт. Ручной сценарий неоднозначной комнаты:
`node research/check-agent-room-ambiguity.mjs ambiguous`.

## Бытовые задачи внешним агентом

`eval:agent` даёт внешнему агенту бытовую просьбу и проверяет, справился ли он
через поставляемый плагин и сколько контекста потратил. Хаб заменяет
симулятор `test/support/simulated-hub.mjs`. Дома: `apartment` (квартира,
`test/fixtures/homes/apartment.json`) и `house` (дом примерно вдвое больше
дома владельца, `test/fixtures/homes/house.mjs`; содержит квартиру с теми же
id). Факты грейдеры проверяют детерминированно: записи и итоговое состояние
симулятора, выполнение созданных BLOCK-правил, сырые идентификаторы и нужные
числа в ответе. Смысл ответа (причина, отказ, честное «не подтверждено»,
список включённого) оценивает модель-судья `research/eval-judge.mjs`: один
вызов `claude -p` без инструментов на ответ, с фактами этого прогона и
критериями задачи из `research/eval-agent-cases.mjs`. Судья обязан
процитировать фрагмент ответа, на котором основан вердикт. Прогон вызывает
модели, поэтому в `npm run check` не входит; там проверяются симулятор,
грейдеры и связка раннера со скриптовыми агентом и судьёй.

```sh
npm run eval:agent -- read-temperature                 # Claude Code, sonnet
npm run eval:agent -- all --harness claude --model opus
npm run eval:agent -- whats-on,turn-off-room --fixture apartment,house --repeat 3
npm run eval:agent -- all --harness codex
npm run eval:agent -- turn-off-room --plugin-dir /path/to/other/dist/plugin
npm run eval:agent -- --help                           # список задач и флагов
```

Судья получает явный id модели (`--judge-model`, по умолчанию
`claude-sonnet-5`), и прогон проверяет, что CLI ответил той же моделью.
Псевдонимы `sonnet` и `opus` у агента раскрывает установленная версия Claude
Code CLI (у 2.1.150 `opus` давал claude-opus-4-7), поэтому для сравнимых
прогонов передавайте `--model` с полным id.

Судью калибруют на размеченных ответах `research/eval-judge-labels.mjs`
(не меньше пяти верных и пяти неверных на задачу, с причиной метки):

```sh
npm run eval:judge-calibrate                            # все метки, claude-sonnet-5
npm run eval:judge-calibrate -- --case whats-on --model claude-opus-5-5
npm run eval:judge-calibrate -- --ids why-night-light/no-time,whats-on/desk-lamp-off
```

`--ids` принимает `<задача>/<id>`: id записан в самой метке и не меняется,
когда метки добавляют. Если факты судьи зависят от того, что агент отправил
хабу, метка несёт эти запросы (`sent`): калибровка отправляет их симулятору
до вызова судьи.

Команда печатает согласие по задачам (отдельно для меток `ambiguous`) и
каждое расхождение с цитатой и причиной судьи и завершается ошибкой, если
разошлась однозначная метка. Каждая метка — вызов модели, поэтому в
`npm test` входит только прогон со скриптовым судьёй. Новую задачу с
судьёй или правку её критериев сопровождают метки и калибровка.

`claude` запускает `claude -p` с плагином из `--plugin-dir` (по умолчанию
`dist/plugin`), без пользовательских настроек и чужих MCP; агенту доступны
только инструменты `sprut-agent`, Skill и Read. Нужен действующий вход
Claude Code CLI. Задача с несколькими репликами идёт одной сессией
(`--session-id`, затем `--resume`); её транскрипт в `~/.claude/projects`
удаляется по id. `codex` ставит тот же каталог через временный marketplace в
изолированный профиль, берёт `~/.codex/auth.json` и запускает команды агента в
профиле прав, который читает только системные пути, рабочий каталог и
установленный плагин. `--plugin-dir` на detached worktree другого коммита
сравнивает две сборки.

Задача может включить сбои хаба (`faults`: запоздалое чтение, потерянный
ответ, устройство офлайн, активная логика лампы) и поменять исходный дом
(`patch`). Каждый прогон получает свои токен и client id хаба; второе
подключение к хабу, чужой client id, чтение репозитория вне плагина или
метод, которого нет в симуляторе, проваливают прогон как `isolation` или
`simulator_gap`, а не как ошибку агента. Ответ судьи, который нельзя
проверить (цитаты нет в ответе, ответ вне схемы, ошибка или таймаут CLI,
другая модель), проваливает прогон как `judge_error`: это не успех и не
ошибка агента, если другие грейдеры задачи прошли. Созданное правило грейдер
исполняет по шагам BLOCK в окне 10 с после события. Удержание «не менялось
N» на только что изменившейся характеристике при N не меньше окна в этом
окне ложно («нет движения 5 минут — выключить»). Если исполнимая часть уже
нарушает задачу (пишет в чужое устройство, гасит свет по движению), прогон
проваливается как ошибка агента. Иначе форму, которую грейдер не моделирует
(другое удержание, повтор ветки, задержка не в режиме RESET, код), он не
угадывает: прогон проваливается как `grader_unsupported`. Так же, если
триггер стоит во вложенном «Если» (по вики вендора он запускает только свою
часть) и это расходится с прогоном всего BLOCK. Задачи с `pending`
(недостающая возможность ещё не в main) в `all` не входят без
`--include-pending`; задачи с
`expectedFail` ждут исправления продукта, их итог виден как XFAIL/XPASS и не
проваливает прогон.

Каждый прогон пишет в каталог вне репозитория `result.json` (грейдеры, класс
провала, вердикт, цитата и критерии судьи, MCP-вызовы и их байты, запросы к
хабу и байты его ответов, все вызовы, токены, время, версия CLI и
фактическая модель, отдельно токены и стоимость судьи, идентичность плагина
по `server_sha256`, методы симулятора с уровнем доказанности
`observed`/`schema_only`/`guess`, сработавшие сбои), транскрипт и запросы к
симулятору. Успех, который опирается на метод без живого подтверждения,
печатается как `PASS* (unverified: service.update)`. `summary.json` и строки
`SUMMARY` сводят повторы по задаче и дому: отдельно PASS, PASS* и FAIL,
медианы MCP-вызовов, MCP-байтов, запросов к хабу, байтов его ответов и
токенов отдельно для успешных (`passed`, вместе с PASS*) и проваленных
(`failed`) прогонов. Отношение house/apartment (`SCALE`) считается только по
успешным прогонам; без успеха на одном из домов его нет. Вызовы и стоимость
судьи сведены отдельно (`judge`, строка `JUDGE`). Для сравнения между Claude
и Codex берутся MCP-вызовы и MCP-байты: собственные инструменты агентов
разные. Запросы и
байты хаба показывают, во что тот же ответ обошёлся хабу: MCP-сервер может
скачать весь каталог дома ради одного сценария.
Симулятор не настоящий SprutHub: успешный прогон не заменяет живую приёмку.

## Соответствие настоящему хабу

`npm run conformance:live` проверяет собранный `dist/plugin` на хабе из
`connection.env`: создание, readback и удаление комнаты и имена комнат с
кириллицей и emoji, BLOCK-формы по контракту и формы `if` веб-клиента,
частичные изменения BLOCK, включение и выключение BLOCK и LOGIC через окно
сценария, жизненный цикл LOGIC и его тип в `logic.types`, проверку дубля
`virtual_light_group` без записи, ручной запуск выключенного и включённого
BLOCK, одно срабатывание ежедневного времени (шаг ждёт около трёх минут); ещё
он читает окна сценариев владельца, `history.list` и время первых чтений.
Сценарии скрипт называет
префиксом `zz-sprut-agent-probe-<время>`, а комнаты и один виртуальный
Lightbulb без links — коротким именем `zz-probe-<время>`: хаб хранит только
30 символов их имён. BLOCK действуют только на этот виртуальный аксессуар,
срабатывают только от one-date cron 2030 года или одного времени в сутки и
создаются выключенными. LOGIC прогона ничего не исполняет (объект `info` и
пустой `trigger`), включается только без назначений и назначается только на
виртуальный аксессуар и только выключенным. В конце скрипт удаляет всё
созданное; снимок дома до и после должен совпасть. Отчёт и журнал изменений
лежат во временном каталоге вне репозитория. Запускать только с разрешения
владельца дома.

Удаление идёт через `restore_native_change`. Аксессуар, BLOCK и одну
комнату, которые скрипт создаёт в обход продукта (выключенный action-only,
формы `if`, имя комнаты длиннее 30 символов), он удаляет сам; у таких BLOCK
в описании есть маркер той же формы. Объект прогона, который остался после
этого, скрипт удаляет напрямую клиентом продукта, если прогон доказуемо его
создал и объект не может сработать: сценарий с маркером продукта и
`active=false`, пустая комната из `room_create` журнала прогона или с id из
`probe-rooms.json`, виртуальный аксессуар без links, чей id записан в
`probe-accessories.json` каталога журнала. Каждый такой объект — провал
прогона, кроме выключенного LOGIC, который шаг 4 оставил уборке, потому что
restore продукта его не удалил; остальные объекты с именами прогона только
перечисляются.
`-- --sweep-only <префикс> --state-dir <каталог>` повторяет эту уборку для
прошлого прогона; каталог журнала печатается в конце прогона, без него
комнаты и аксессуар только перечисляются.

`-- --read-only` выполняет только шаги чтения `Vp, 2w, 7, 8` и снимки; любую
запись скрипт отклоняет до отправки. `-- --only 2i,7` выполняет только
перечисленные шаги из `1, 1n, V, Vp, Vd, 2, 2i, 2w, 3, 4, 6, 6t, 7, 8`; шаг,
которому нужен пропущенный, отмечает себя blocked.
Результаты прогонов — в [research/protocol/](research/protocol/).

## Код, исполняемый на хабе

Перед созданием LOGIC агент вызывает `get_scenario_sdk` и получает текущие
декларации sandbox выбранного хаба. `sdk_complete=true` означает полный `sdk`,
`false` — частичное содержимое с защитным marker. `bytes` и `sha256` описывают
фактически возвращённый текст, freshness — время ответа. Это API кода на хабе,
а не Node или browser SDK; локально код не исполняется.

## Исследование протокола

| Команда | Результат |
| --- | --- |
| `npm run research:diff -- --from <снимок> --to <снимок>` | Сравнение схем и каталога операций |
| `npm run research:record -- --cdp-url http://127.0.0.1:9222` | Пассивная запись WebSocket-событий через Chrome DevTools Protocol |
| `npm run research:snapshot` | Попытка извлечь схемы и метаданные из публичной сборки |

Recorder требует отдельную браузерную сессию с CDP и ручную авторизацию. Raw
captures сохраняются с правами `0600` в исключённом из Git каталоге и могут
содержать секреты; санитайзер не реализован.

Снимок `1.5.58` относится к сборке 2025-09-16. Полный snapshot CLI на текущей
публичной сборке останавливается на распознавании build; отдельная функция
извлечения protobuf-модулей текущий JS читает. Источники, версии и границы
достоверности — в [research/protocol/](research/protocol/). Исторические
черновики лежат в [research/archive/](research/archive/) и не задают текущий
объём работ.

## Правила и задачи

Git использует Conventional Commits; RED/GREEN, ревью, ветки и рабочая копия
описаны в [AGENTS.md](AGENTS.md). Задачи, результаты и приёмка ведутся в
[проекте SPRUT](https://plan.nuanu.ai/project/SPRUT), порядок работы — в
[документе команды](https://plan.nuanu.ai/project/SPRUT/docs/178).

<details>
<summary>Подключение Plan для работы над репозиторием</summary>

Локальный `.codex/config.toml` подключает Plan только в этом репозитории и
исключён из Git:

```toml
[mcp_servers.plan]
url = "https://api-plan.nuanu.ai/mcp"
http_headers = { Authorization = "Bearer ВАШ_КЛЮЧ_АГЕНТА" }
```

Используй ключ внешнего агента с доступом к SPRUT и права `0600`. Для OAuth
убери `http_headers`, выполни `codex mcp login plan` из корня и перезапусти
клиент после изменения конфигурации.

</details>
